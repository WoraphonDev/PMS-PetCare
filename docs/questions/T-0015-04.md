# T-0015-04 · Invitation token, lookup under RLS, and the invitation link and email
- Status: open
- Raised by: claude · T-0015 (card preparation) · 2026-10-22 (revised after review 2026-10-22)
- Context:
  - #tbl-invitation stores only `token_hash` (SHA-256).
  - `invitation` has RLS `tenant_isolation` on `app.org_id`. `invitation.accept` is called by a user who is not yet a member, without `X-Org-Id`, so the runtime role cannot find the row by hash alone.
  - ADR-0003: cross-tenant work uses a separate role/connection. Identity's `membershipsOf` (for `me.get`) reads through the platform connection. There is no index on `token_hash`.
  - #scr-invite-accept fixes the web path as `/invite/:token`: the token would sit in the HTTP request path, where proxy/CDN access logs, browser history and `Referer` headers can expose it.
  - #rule-email-verification-http already moved the verification token to a fragment (`/verify-email#token=…`) for this reason.
  - T-0015 builds the link inside the invitation email, so the link format must be decided before T-0015, not in T-0026. The email text is user-facing Thai and is not in the spec.
  - These are two separate decisions: (1) the **token format** and how accept finds the row; (2) the **link format** in the email.
- Question: How is the token built and found, what link goes in the email, and what does the email say?
- Options:
  - Token format:
    (T1) Token = `<orgId>.<32 random bytes, base64url>`; `token_hash` = hex SHA-256 of the whole token. Accept parses the org id, runs under `withTenant(orgId)` and looks the row up by hash. RLS stays on, no platform connection, no migration. A malformed token, an org id that does not exist, or an org with no matching invitation answers `INVITATION_INVALID` like any unusable token. These are decided in the phase-1 preflight (T-0015-03) before the subscription lock, so a made-up org id never reaches the fail-closed `INTERNAL` of a missing subscription.
    (T2) Random token only; accept looks the hash up through the platform connection, then writes under `withTenant`. Needs an index on `invitation(token_hash)`, so a migration card first.
  - Link format:
    (L1) `${APP_ORIGIN}/invite#token=<token>` (fragment). Browsers do not send the fragment in the request path or in `Referer`. The web page reads it, clears it from history, and POSTs it in the JSON body of `invitation.accept`, as `/verify-email` does. **This changes #scr-invite-accept, so the change must be written in §14 and approved before implementation.**
    (L2) `${APP_ORIGIN}/invite/<token>` as #scr-invite-accept says today.
  - Both link formats: the API takes the token only in the request body of `POST /invitations/accept`, never in a path or query.
  - Email (both): sent after commit through `BackgroundWork` + `EmailSender`. A send failure is logged without token or address and does not change the response.
    - Subject: `คำเชิญเข้าร่วมร้าน <displayName>`.
    - Body: shop name, role label (th), "ลิงก์นี้ใช้ได้ครั้งเดียวและหมดอายุใน 7 วัน", the link.
    - The exact Thai text is approved in §14.
  - Limits that stay true: the application log-capture tests (pino, Nest Logger, console) only show that **our** process does not log the token. They do not show that a proxy, CDN, mail provider or browser keeps it private. L1 reduces that exposure; it does not remove it (the token is still in the email).
  — แนะนำ: T1 + L1. T1 keeps every tenant read behind RLS without a migration; the org id inside the token is not secret, since the invitee learns the shop anyway. L1 follows the approved verification-link precedent and keeps the token out of request paths and `Referer`.
