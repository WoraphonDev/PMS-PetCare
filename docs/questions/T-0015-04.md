# T-0015-04 · Invitation token, lookup under RLS, and the invitation email
- Status: open
- Raised by: claude · T-0015 (card preparation) · 2026-10-22
- Context: #tbl-invitation stores only `token_hash` (SHA-256). `invitation` has RLS `tenant_isolation` on `app.org_id`, and `invitation.accept` is called by a user who is not yet a member, without `X-Org-Id`, so the runtime role cannot find the row by hash alone. ADR-0003: cross-tenant work uses a separate role/connection. Precedent: identity's `membershipsOf` (for `me.get`) reads memberships through the platform connection. There is no index on `token_hash`. #scr-invite-accept fixes the web path as `/invite/:token` (token in the URL path, which can end up in proxy logs and Referer headers; email verification moved its token to a fragment). The email text is user-facing Thai and is not in the spec.
- Question: How is the token built and found, what link goes in the email, and what does the email say?
- Options:
  (A) Token = `<orgId>.<32 random bytes, base64url>`; `token_hash` = hex SHA-256 of the whole token. Accept parses the org id, runs under `withTenant(orgId)` and looks the row up by hash (RLS stays on, no platform connection, no migration). Link `${APP_ORIGIN}/invite/<token>` as #scr-invite-accept says. Email is sent after commit through `BackgroundWork` + `EmailSender`; a send failure is logged without token or address and does not change the response. Subject `คำเชิญเข้าร่วมร้าน <displayName>`; body: shop name, role label (th), "ลิงก์นี้ใช้ได้ครั้งเดียวและหมดอายุใน 7 วัน", the link.
  (B) Random token only; accept looks the hash up through the platform connection (like `membershipsOf`), then writes under `withTenant`. Needs an index on `invitation(token_hash)` (migration in a separate card first).
  (C) As A, but change #scr-invite-accept to a fragment link `/invite#token=<token>` (spec change, like `/verify-email`).
  — แนะนำ: A for the API card, and decide C separately for T-0026: A keeps every tenant read behind RLS without a migration. The org id in the token is not secret (the invitee learns the shop anyway). C is safer for the web link and only affects the URL the email builds and the screen; if C is chosen, T-0015 builds the fragment link instead.
