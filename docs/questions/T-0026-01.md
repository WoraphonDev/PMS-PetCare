# T-0026-01 · signup.test.ts times out in CI and blocks PR #83
- Status: open
- Raised by: claude · T-0026 · 2026-10-25
- Context:
  - PR #83 (T-0026) changes only `apps/pms-web/**` and `packages/api-client/**`. CI `verify` failed twice in a row (run 40163722430, attempts 1 and 2), both times in `apps/api/test/identity/signup.test.ts`:
    - `POST /auth/signup` › "rate-limits the sixth schema-valid attempt from one IP (#rule-signup-abuse)" → `Test timed out in 5000ms` (six sequential signups, each one hashes a password).
    - atomicity › "leaves no row and sends no message when identity fails" → a knock-on failure: the timed-out test's last signup finishes late, and its verification email lands in this test's message collector.
  - On main (last green run) the same test takes 3716 ms out of the 5000 ms default, so there is little headroom. T-0026 adds 40 web tests and 5 api-client tests, and `pnpm verify` runs every package's tests in parallel. That extra CPU load pushes this API test over the limit.
  - This is the same failure as T-0039 (2FA tests) and T-0050 (`platform.orgs` tests). The fix is in `apps/api/test/identity/signup.test.ts`, which is outside T-0026's `allowed_paths`.
- Question: How should the failing signup test be fixed so that PR #83 can pass CI?
- Options:
  (A) A small `test` card, same pattern as T-0039/T-0050. It gives every multi-step `it(...)` in `apps/api/test/identity/signup.test.ts` an explicit per-test timeout through one named constant (e.g. `MULTI_STEP_TIMEOUT_MS = 20_000`), including the rate-limit test and the concurrent/atomicity tests. It is test-only: no assertion or production change. PR #83 waits for it, then syncs main.
  (B) Add `apps/api/test/identity/signup.test.ts` to T-0026's `allowed_paths` and make the same change inside PR #83. One PR fewer, but it mixes an API test fix into a web card.
  (C) Raise the default `testTimeout` in `apps/api/vitest.config.ts` for all API tests. This also covers the next borderline test, but it hides real slowness everywhere and changes shared config.
  — Recommended: A. It is the precedent the human already approved twice, it keeps the web PR scoped, and it applies the timeout only where a test is legitimately multi-step.
