# T-0015-03 · F05 max_staff: what counts and how it is locked
- Status: open
- Raised by: claude · T-0015 (card preparation) · 2026-10-22
- Context: foundation#rule-F05: inviting beyond `max_staff` → `PLAN_LIMIT_REACHED`, "คำเชิญที่ยังค้างนับรวม". F09: managed accounts count in `max_staff`. `mvp_free` has `max_staff 5` (Q-0005). Not defined: whether the owner counts as staff, whether expired invitations count, whether a re-invite (which revokes the old row) counts twice, whether accept re-checks the limit, and how concurrent invites are serialised. #rule-branch-capacity solved the same problem for branches by locking the subscription row (`lockBranchLimit`).
- Question: How is the staff count computed and enforced?
- Options:
  (A) count = `membership` rows with `status = 'active'` (all roles, owner included) + `invitation` rows with `accepted_at` null, `revoked_at` null and `expires_at > now`. When the invite replaces an unexpired invitation for the same email, the old one is not counted. `count >= max_staff` → `PLAN_LIMIT_REACHED` (402) with no row, audit or email. `max_staff` null = unlimited. A new `subscription` public function `lockStaffLimit` locks the subscription row `FOR UPDATE` before counting (same lock as branch create, so concurrent invites serialise). No subscription → `INTERNAL`. Accept does not re-check (the seat was reserved at invite time). T-0016 `staff.account.create` uses the same function.
  (B) Same as A, but the owner(s) are not counted (5 = staff besides the owner).
  (C) Same as A, but accept re-checks and returns `PLAN_LIMIT_REACHED` if the plan was lowered after the invite.
  — แนะนำ: A. "พนักงาน" in `subscription.get` (#ep-subscription.get) and the plan is easiest to explain as "people with access", and A matches the existing branch-capacity lock. Choose B if pricing intends "1 owner + 5 staff".
