# T-0015-03 · F05 max_staff count and the shared lock protocol
- Status: answered
- Raised by: claude · T-0015 (card preparation) · 2026-10-22 (revised after review 2026-10-22)
- Context:
  - foundation#rule-F05: inviting beyond `max_staff` → `PLAN_LIMIT_REACHED`, "คำเชิญที่ยังค้างนับรวม".
  - F09: managed accounts count in `max_staff`. `mvp_free` has `max_staff 5` (Q-0005).
  - #rule-branch-capacity solved the same problem for branches by locking the subscription row (`lockBranchLimit`).
  - Not defined:
    - whether the owner counts;
    - whether expired invitations count;
    - whether a re-invite counts twice;
    - whether accept re-checks the limit;
    - how invite, re-invite, accept and revoke are serialised against each other.
  - Read committed gives each statement its own snapshot. If invite counted memberships and invitations in two queries while an accept committed between them, the accept's "−1 pending, +1 active" could be seen only half, and the limit could be passed.
- Question: How is the staff count computed, and which locks do the seat-changing operations take?
- Options:
  (A) Count and locks:
    - count = active `membership` rows (all roles, owner included) + `invitation` rows with `accepted_at` null, `revoked_at` null and `expires_at > now`.
    - The count is computed **in one SQL statement**.
    - When the invite replaces an unexpired invitation for the same email, the old one is not counted.
    - `count >= max_staff` → `PLAN_LIMIT_REACHED` (402), with no row, audit or email. `max_staff` null = unlimited. No subscription → `INTERNAL`.
    - Shared check-and-lock protocol, in two phases.
    - **Phase 1, before any tenant lock** (no writes):
      - authentication and guards;
      - request validation and request-only role rules;
      - for accept also: token parsing, the managed/verified-email checks of T-0015-05, and a tenant preflight. The preflight reads the invitation by hash without locking it. If the org does not exist, nothing matches, or the invitation is unusable → `INVITATION_INVALID`, then org suspended → `ORG_SUSPENDED`, all before lock 1 is ever taken.
    - **Phase 2, in one tenant transaction** (the same one as the preflight for accept). Locks in this order; a step an operation does not need is skipped, never reordered:
      1. the org's `subscription` row `FOR UPDATE`, through a new subscription public function `lockStaffLimit` (the same row `lockBranchLimit` locks). A missing row → `INTERNAL` (fail closed). For accept this is reached only when the org and a matching invitation exist, so it signals broken data and must not be turned into `INVITATION_INVALID`;
      2. the `invitation` rows involved, `FOR UPDATE`, in id order;
      3. the `membership` row of (org, user) `FOR UPDATE` when it exists.
      Every writer takes the same order, so they cannot deadlock each other or branch create.
    - After the locks and before any write, each operation checks the state it depends on, again for anything phase 1 read. The first failing check answers, and a failure rolls everything back.
      - invite: branch ids → `NOT_FOUND`; manager vs. pending owner/manager invitation → `FORBIDDEN`; active membership → `ALREADY_MEMBER`; seat count → `PLAN_LIMIT_REACHED`.
      - revoke: state → `NOT_FOUND`; manager rule → `FORBIDDEN`.
      - accept: invitation state, expiry, email → `INVITATION_INVALID`; org status again → `ORG_SUSPENDED`; membership → `ALREADY_MEMBER`.
    - Which operations take which locks:
      - invite and re-invite: 1, 2 (pending rows for that email), 3 (`ALREADY_MEMBER` check).
      - accept: 1, 2 (its row), 3.
      - revoke: 1, 2 (its row).
      - T-0016 `staff.account.create` and T-0017 `staff.remove`/`staff.update`: 1 and 3.
    - **Accept does not re-check the limit, and that is separate from the lock.** It never compares against `max_staff`, because the seat was reserved at invite time. It still takes lock 1, only to serialise the seat changing from "pending invitation" to "active membership" against invite's count and re-invite's revoke. A plan lowered after the invite does not cancel pending invitations or block their accept.
  (B) Same as A, but the owner(s) are not counted (5 = staff besides the owner).
  (C) Same as A, but accept re-checks and returns `PLAN_LIMIT_REACHED` if the plan was lowered after the invite (a policy change, not a locking change).
  (D) Same as A, but accept and revoke skip lock 1 and rely on the invitation row lock only. This is correct only if the count is a single statement. It is less obviously safe and leaves two lock orders in the module.
  — แนะนำ: A. One lock order for every seat change is easy to check and matches branch create. "พนักงาน" in the plan and in `subscription.get` is easiest to explain as "people with access". Choose B if pricing intends "1 owner + 5 staff".
- Answer: 2026-10-22 · human chose (A) in chat: count = active memberships (owner included) + unexpired pending invitations in one SQL statement; the shared two-phase check-and-lock protocol; accept holds the subscription lock to serialise but does not re-check the limit. Spec: foundation#rule-staff-check-and-lock, foundation#rule-staff-capacity.
