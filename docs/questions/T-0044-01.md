# T-0044-01 · Invitation preview: how does `/invite` show the shop name and role before accepting?
- Status: open
- Raised by: claude · T-0044 (card preparation) · 2026-10-24
- Context:
  - `#scr-invite-accept` (`/invite#token=…`): "แสดงชื่อร้าน + role; login แล้วรับคำเชิญ; สมัครแล้วรับคำเชิญ". The screen must show the shop and role **before** the user accepts or signs up.
  - The only invitation endpoint for invitees is `POST /invitations/accept` (logged-in, writes a membership). Its 200 `{ orgId, membershipId, role, branchIds }` comes **after** accepting. `staff.list` needs `X-Org-Id` and membership. So nothing returns the shop name to a person who only holds the token.
  - The token is `<orgId>.<32 random bytes>`; the API stores only its SHA-256 hash (#rule-invitation-token). It must travel only in a JSON body, never a path/query.
  - The invite-bound signup (T-0044-02) also needs to know the invitation is valid and which email it is for before asking for a password.
- Question: Add a public read of an invitation by token? If so, what does it return?
- Options:
  (A) **New public endpoint `invitation.preview`:** `POST /invitations/preview` · public (no session, no `X-Org-Id`) · strict body `{ token }` (1–200) · checks like `invitation.accept` steps 3 and 6 without locks or writes (malformed, not found, used, revoked, expired → `INVITATION_INVALID`; suspended shop → `ORG_SUSPENDED`) · 200 `{ orgDisplayName, role, branchNames, email, expiresAt }` — `email` is the invited address (the token holder received it at that address) so the UI can say "คำเชิญนี้สำหรับ a@b.com"; `branchNames` only of that invitation's branches. **No** field says whether an account already exists for the email (the UI always offers both "log in" and "sign up"). No audit, no rate limit beyond existing defaults (the token has 256 random bits). Implemented in T-0044.
  (B) Same as A, but without `email` (UI cannot warn about logging in with the wrong account; the user finds out from `INVITATION_INVALID` on accept).
  (C) No preview: change §7 so `/invite` shows shop and role only after accepting (from the accept response + `me.get`). No new endpoint, but the invitee accepts blind, and the signup path cannot show which email it will use.
  — แนะนำ: A. It is a read-only check of something the holder already proved they own, it gives the screen what §7 asks for, and it lets both the logged-in and the sign-up paths fail early with a clear message.
