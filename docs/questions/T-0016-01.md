- Context:
  - foundation#ep-staff.account.create: `POST /staff/accounts` · `staff.invite` · `{ displayName, username, password, role, branchIds }` · F02, F05, F09 · `CONFLICT` when the username is taken · audit `staff.account_created`.
  - #tbl-identity: `username` citext, unique platform-wide, `^[a-z0-9._-]{3,40}$`. F11: password 10–128 characters. ¹: a manager cannot make anyone owner/manager.
  - #rule-staff-check-and-lock names T-0016 as a seat-changing writer (subscription lock first); #rule-staff-capacity counts managed accounts.
  - #contract-staff-invite already fixes the `branchIds` rules for invitations (unique UUIDs, owner/manager `[]`, unknown in tenant → `NOT_FOUND`).
  - Not defined:
    - the response status and body;
    - username normalisation (trim? lower-case?) and `displayName` limits;

    - the error precedence, incl. where `CONFLICT` sits relative to `PLAN_LIMIT_REACHED`;
    - the audit `before`/`after`.
- Question: What exactly does `POST /staff/accounts` accept, check (in which order), write and return?
- Options:
  (A) Strict body per §11:
    - `displayName`: trimmed, 1–100 (like branch names); becomes both `membership.display_name` and `user.name`.
    - `username`: trimmed and lower-cased, then `^[a-z0-9._-]{3,40}$` (the DB rule); never an email.
    - `password`: F11 length 10–128, not trimmed.
    - `role` and `branchIds`: exactly as in #contract-staff-invite.
    - Check order (first failure answers):
      1. guards;
      2. body → `VALIDATION_FAILED`;
      3. manager asking owner/manager → `FORBIDDEN`;
      4. branch role without branches → `BRANCH_REQUIRED`;
      5. phase 2: lock subscription (missing → `INTERNAL`), re-read org status → `ORG_SUSPENDED`;
      6. branch ids not in the tenant → `NOT_FOUND`;
      7. seat count (#rule-staff-capacity) → `PLAN_LIMIT_REACHED`;
      8. username already used by any account → `CONFLICT` (checked, and also mapped from the unique violation if two creates race).
    - Write in one transaction: the managed account (T-0016-02), membership (`status 'active'`), `membership_branch` rows, audit `staff.account_created` (`entity_type 'membership'`, `entity_id` = membership id, `before` null, `after { username, displayName, role, branchIds }`; never the password or its hash).
    - Response **201** `StaffMember` (the #contract-staff-list shape; `email` null, `isManaged` true).
  (B) Same as A, but `CONFLICT` (step 8) before `PLAN_LIMIT_REACHED` (step 7).
  (C) Same as A, but the username keeps its case as typed (only checked against the regex, which already rejects upper case).
  — แนะนำ: A. It reuses the invite rules and response shape, so the web treats both ways of adding staff the same. A full plan answers before a username check, so a shop at its limit learns that first. Lower-casing before the regex lets "Mai.K" become "mai.k" instead of a rejection, and matches the citext uniqueness.
