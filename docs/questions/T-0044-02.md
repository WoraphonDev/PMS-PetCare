# T-0044-02 · Invite-bound signup: what does it create, verify and return?
- Status: answered
- Raised by: claude · T-0044 (card preparation) · 2026-10-24
- Context:
  - `#rule-invite-signup-followup`: invitees without an account need "การสมัครที่ผูกกับ token คำเชิญ (สร้างเฉพาะ user ไม่สร้างร้าน)"; `auth.signup` must never be used as a workaround (it always creates a shop).
  - `auth.signup` creates user + shop and requires email verification before login (#rule-email-login-policy); verification links are sent after commit (#rule-email-verification-http).
  - F03: an invitation is single-use, expires in 7 days, and the accepting user's email must equal the invited email. The invitation email was sent to that address, so holding the token shows control of that inbox.
  - `invitation.accept` already defines the membership write and audit `staff.joined`; it does not check `max_staff` (the pending invitation already counted).
  - Abuse limits: signup has 5 attempts / hour / trusted IP (#rule-signup-abuse) with its own key prefix.
- Question: How does an invitee without an account sign up and join?
- Options:
  (A) **One public call creates a verified user and joins:** `POST /auth/signup/invitation` · public · strict body `{ token, displayName, password }` (no email — it comes from the invitation; `displayName` 1–100; password F11 10–128).
    - In one transaction: validate the invitation like `invitation.accept` (→ `INVITATION_INVALID` / `ORG_SUSPENDED`); an account with that email already exists → `CONFLICT` (the person must log in and accept instead); create the user with `emailVerified = true` (the token proves the inbox) and `isManaged = false`; then the accept write of `invitation.accept` (membership, branches, `accepted_at`, audit `staff.joined` with the new user as actor).
    - 201 `{ orgId, role }`, **no session** — the user logs in next (2FA/F10 as usual).
    - Abuse limit: same numbers as signup (5 / hour / trusted IP) with its own key prefix `signup-invite`; counted before the transaction; over → `RATE_LIMITED`.
    - No verification email is sent.
  (B) Same as A, but the user is created **unverified**, a verification email is sent after commit, and the membership is created at once (the user can log in only after verifying). Consistent with normal signup, one extra email round-trip for someone who just clicked an emailed link.
  (C) Same as A, but the response also **logs the user in** (session cookie). Smoothest, but adds a second session-creating path next to `auth.login` (2FA cannot apply to a brand-new account, but the login rate limits and policy checks would be duplicated).
  — แนะนำ: A. The invitation link already proves the email; asking for a second email is friction with no security gain. No auto-login keeps exactly one place that creates sessions. `CONFLICT` for existing accounts keeps "log in, then accept" as the single path for them.
- Answer: 2026-10-24 · human chose (A) in chat: `POST /auth/signup/invitation` `{ token, displayName, password }` creates a verified, non-managed user with the invitation's email and joins in one transaction (audit `staff.joined`); existing account → `CONFLICT`; 5 / hour / trusted IP (prefix `signup-invite`); 201 `{ orgId, role }`, no session, no email.
