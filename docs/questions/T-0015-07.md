# T-0015-07 · staff.invitation.revoke semantics, locking and audit
- Status: open
- Raised by: claude · T-0015 (card preparation) · 2026-10-22 (revised after review 2026-10-22)
- Context:
  - foundation#ep-staff.invitation.revoke: `DELETE /staff/invitations/{invitationId}`, permission `staff.invite`, nothing else.
  - ¹: a manager cannot act on owners/managers. F07: another org's id → `NOT_FOUND`.
  - §6 has no audit action for revoking an invitation, and agents must not invent one.
  - #contract-branch-schedule-common (§12) already defines DELETE routes as 204 without a body.
  - Revoke can race accept of the same invitation; the outcome must match whichever commits first.
- Question: What does revoke return for each state, how is it serialised against accept, and is it audited?
- Options:
  (A) Base:
    - 204, no body (body/query handled like the §12 DELETE routes).
    - The two phases of T-0015-03:
      - phase 1 (no lock): guards incl. `ORG_SUSPENDED`; `invitationId` not a UUID → `VALIDATION_FAILED`;
      - phase 2, one tenant transaction: lock the subscription row (missing → `INTERNAL`), then the invitation row `FOR UPDATE`, then check in this order before any write: absent, other org, accepted, revoked or expired → `NOT_FOUND`; a manager caller and an `owner`/`manager` invitation → `FORBIDDEN`.
    - Pending → set `revoked_at = now`, `updated_at = now`.
    - The same manager rule applies when a re-invite would revoke an owner/manager invitation (T-0015-02).
    - Race outcome: revoke commits first → accept then sees `revoked_at` → `INVITATION_INVALID`, no membership. Accept commits first → revoke sees `accepted_at` → `NOT_FOUND`, membership stays.
    - No audit row (§6 has no action); the row keeps `revoked_at` as the record.
  (B) Same as A, plus a new audit action `staff.invitation_revoked` added to §6 by this decision.
  (C) Same as A, but revoking an already revoked/expired invitation is an idempotent 204.
  — แนะนำ: A, unless the human wants revocations in the audit log, in which case B (the action name must then be added to §6 in the §14 merge). `NOT_FOUND` for unusable invitations matches the list, which only shows pending ones.
