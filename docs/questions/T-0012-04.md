# T-0012-04 · F05 branch capacity semantics
- Status: open
- Raised by: claude · T-0012 · 2026-10-21
- Context: foundation#rule-F05: creating a branch beyond `max_branches` → `PLAN_LIMIT_REACHED`. foundation#tbl-plan: `max_branches` null = unlimited; `max_staff` explicitly "นับ membership `active`" but `max_branches` has no counting rule — it is unspecified whether branches with `is_active = false` count. Also unspecified: org with no subscription row, subscription whose plan has `is_active = false`, and a `current_period_end` in the past (column says null = never expires in MVP). The card forbids inventing a subscription error code and direct org→subscription table reads. Concurrency: the card requires at most one commit with one slot left; the existing `startFreeSubscription` reads plans on the caller's tenant transaction.
- Question: How is branch capacity counted, and what happens when the subscription/plan is missing, inactive or expired?
- Options:
  (A) Count all branch rows of the org (active and inactive — deactivating does not free a slot). Missing subscription row → fail closed as `INTERNAL` (data integrity violation, signup always creates one). Plan `is_active = false` or past `current_period_end` → still enforce that plan's `max_branches` (no lifecycle behaviour in MVP). Concurrency: `subscription.checkBranchCapacity(txCtx)` locks the org's subscription row `FOR UPDATE` inside the same tenant transaction before counting, so concurrent creates and future plan changes serialize on it.
  (B) Count only `is_active = true` branches (deactivating frees a slot); otherwise as A.
  (C) As A but missing/expired subscription → `PLAN_LIMIT_REACHED` (treat as zero capacity).
