# T-0015-01 · staff.list response shape and visibility
- Status: open
- Raised by: claude · T-0015 (card preparation) · 2026-10-22
- Context: foundation#ep-staff.list says only "membership + คำเชิญที่ค้าง" with permission `staff.read` (owner, manager, front_desk). #scr-staff lists the columns: name, email or username, role, branches, status, 2FA, plus pending invitations. Nothing defines the JSON shape, whether `removed` memberships are listed, whether front_desk (a branch role) sees only staff of its own branches (F02 says branch roles see/edit only their branch's data), what "pending" means for invitations, or the order. Managed accounts store an internal `<user_id>@managed.invalid` email that must never be shown (#tbl-identity). Name, email, username and 2FA live in identity tables, so org needs a read-only identity public function (ADR-0002).
- Question: What does `GET /staff` return, and who sees which rows?
- Options:
  (A) 200 `{ members: StaffMember[], invitations: PendingInvitation[] }`, no pagination. `StaffMember = { membershipId, userId, displayName, email (null for managed), username (null if none), role, branchIds, status, isManaged, twoFactorEnabled, createdAt }`, only `status = 'active'`. `PendingInvitation = { id, email, role, branchIds, expiresAt, invitedByUserId, createdAt }`, only rows with `accepted_at` and `revoked_at` null and `expires_at > now`. front_desk sees the same full list read-only (the screen is a staff directory). Order: role rank (owner → caretaker), then `displayName`, then id; invitations by `createdAt` desc.
  (B) Same shape as A, but front_desk sees only members who share at least one branch with it, plus all owners/managers, and only invitations whose `branchIds` overlap its branches.
  (C) Same as A, plus `removed` members with `status: 'removed'` (history in the list).
  — แนะนำ: A. The screen spec gives front_desk read access to the staff page without a branch filter, and the list holds no customer data. B is the stricter reading of F02 if the human prefers it. Removed members belong in the audit log, not the working list.
