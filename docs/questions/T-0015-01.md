# T-0015-01 · staff.list response shape and visibility
- Status: open
- Raised by: claude · T-0015 (card preparation) · 2026-10-22 (revised after review 2026-10-22)
- Context:
  - foundation#ep-staff.list says only "membership + คำเชิญที่ค้าง", with permission `staff.read` (owner, manager, front_desk).
  - #scr-staff lists the columns: name, email or username, role, branches, status, 2FA, plus pending invitations.
  - #rule-F02: branch roles (`front_desk`/`groomer`/`caretaker`) "เห็น/แก้ได้เฉพาะข้อมูลของสาขานั้น"; owner/manager see every branch. Having `staff.read` grants access to the endpoint; it does not by itself widen F02.
  - Not defined: the JSON shape, whether `removed` memberships are listed, what "pending" means, the order, and what front_desk sees.
  - Managed accounts store an internal `<user_id>@managed.invalid` email that must never be shown (#tbl-identity).
  - Name, email, username and 2FA live in identity tables, so org reads them through an identity public function (ADR-0002).
- Question: What does `GET /staff` return, and which rows and fields does each caller see?
- Options:
  (A) Shape S below. front_desk sees the same full list as owner/manager, read-only. **This is an exception to F02** and needs explicit human approval; it cannot be inferred from `staff.read`.
  (B) Shape S below, branch-scoped for front_desk, consistent with F02:
    - owner/manager callers see every active member and every pending invitation.
    - A front_desk caller sees:
      - active members of a branch role whose `branchIds` overlap the caller's branches;
      - every active `owner`/`manager` (org-wide roles have no branch assignment, they appear with `branchIds: []` and are shown because they are responsible for every branch, the caller's included);
      - only the branch ids it may see: `branchIds` is the intersection with the caller's branches (other branches are not revealed);
      - pending invitations of a branch role whose `branchIds` overlap the caller's branches, with `branchIds` intersected the same way;
      - no `owner`/`manager` invitations (`branchIds: []`), because they belong to no branch and only owner/manager manage them.
    - Fields: the same for every caller: `email` (null for managed accounts), `username`, `twoFactorEnabled`, as #scr-staff lists. The column set is not reduced for front_desk, because F02 limits rows/branches, not columns. If the human wants to hide `twoFactorEnabled` or `email` from front_desk, that is a new rule to state in §14.
  (C) Same as B, plus `removed` members with `status: 'removed'`.
  - Shape S: 200 `{ members: StaffMember[], invitations: PendingInvitation[] }`, no pagination.
    - `StaffMember = { membershipId, userId, displayName, email (null for managed), username (null if none), role, branchIds, status, isManaged, twoFactorEnabled, createdAt }`, only `status = 'active'`.
    - `PendingInvitation = { id, email, role, branchIds, expiresAt, invitedByUserId, createdAt }`, only rows with `accepted_at` and `revoked_at` null and `expires_at > now`.
    - Order: role rank (owner → caretaker), then `displayName`, then id; invitations by `createdAt` desc, then id.
  — แนะนำ: B. It applies F02 as written without a new exception. Removed members belong in the audit log, not the working list (so not C).
