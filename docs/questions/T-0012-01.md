# T-0012-01 · org.update / org.get wire contract
- Status: answered
- Raised by: claude · T-0012 · 2026-10-21
- Context: foundation#ep-org.update says only "ฟิลด์ใน `tbl-organization` ยกเว้น `slug`, `status`"; foundation#ep-org.get says `Organization`; the DTO paragraph says camelCase columns without internal `org_id`. foundation#tbl-organization gives DB checks only (display_name 1–100, tax_id `^[0-9]{13}$`, receipt_footer ≤ 500) and no rule for `phone`, `legal_name` length, trimming, or clearing a nullable field. `logo_file_id` references the files feature, which has no endpoint/validation yet and is out of scope for this card. The spec also gives no success status/body for PATCH. Precedent: auth.signup trims names and checks 1–100 by PostgreSQL char_length (#rule-signup-input); `me.get` contract uses `.nullable()` for nullable columns.
- Question: What is the exact `PATCH /org` request/response contract?
- Options:
  (A) Request = partial object of `displayName`, `legalName`, `taxId`, `phone`, `receiptFooter` (strict — unknown keys incl. `slug`/`status`/`id`/`logoFileId`/timestamps → `VALIDATION_FAILED`); at least one field required; strings trimmed; `displayName` 1–100 chars; nullable fields accept `null` to clear and empty-after-trim is rejected; `taxId` `^[0-9]{13}$` (no checksum); `receiptFooter` ≤ 500; `legalName`/`phone` ≤ 100 chars, no phone format. `logoFileId` stays read-only until the files feature defines validation. Response 200 with the full `Organization` DTO (`id, slug, displayName, legalName, taxId, phone, logoFileId, receiptFooter, status, createdAt, updatedAt`) — same shape as `GET /org`.
  (B) Same as A but `logoFileId` writable as any UUID or null without existence checks.
  (C) Same as A but no strict-key rejection: unknown/forbidden keys silently ignored.
  — แนะนำ: A (no unvalidated file references; explicit rejection of slug/status matches the card's "Reject org slug/status writes" test). Lengths for legalName/phone are a proposed new rule and need explicit approval.
- Answer: 2026-10-21 · Zo approved option A in chat (recommended), including the proposed `legalName`/`phone` ≤ 100-char limits and `logoFileId` read-only. Needs authoritative spec text before implementation (separate spec/card proposal PR).
