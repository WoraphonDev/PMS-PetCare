# T-0014-01 · branch.paymentSettings.update wire contract (request null, response)
- Status: answered
- Raised by: claude · T-0014 (card preparation) · 2026-10-22
- Context: foundation#ep-branch.payment_settings.update gives only `PUT /branches/{branchId}/payment-settings` · body `{ promptpayId }` · F08 · audit `branch.payment_settings_updated`. No status code or response body. foundation#tbl-branch: `promptpay_id` is nullable. §11 shared rules (strict JSON object, trim before validation, nullable field accepts `null` to clear, empty-after-trim → `VALIDATION_FAILED`) were written for the T-0012 endpoints; the spec does not say whether they cover this endpoint. Existing §11 endpoints accept and ignore query strings; §12 (schedule) rejects them.
- Question: What is the exact request and response contract?
- Options:
  (A) §11 shared rules apply. Body is strict `{ promptpayId }`: the key is required, value is a string that passes F08 after trim, or `null` to clear (branch has no PromptPay). Any other key/type → `VALIDATION_FAILED` + `details.fields.<key>`. Response **200** `Branch` DTO after the change (same shape as `branch.update`). Query strings handled like `branch.update` (no extra rule).
  (B) Same as A but `null` is not accepted: once set, PromptPay can only be replaced, never cleared.
  (C) Same as A but response **200** `{ promptpayId }` projection only, or **204** no body.
  — แนะนำ: A. The column is nullable and `branch.create` sets `null`, so clearing restores the initial state. Returning the `Branch` DTO matches `branch.update` and the DTO already carries `promptpayId` for every `org.settings.read` role (T-0012-02).
- Answer: 2026-10-22 · human chose (A) in chat: strict body `{ promptpayId }`, key required; a string that passes F08 after trim, or `null` to clear; 200 `Branch` DTO; query strings behave as in `branch.update`. Spec: foundation#contract-branch-payment-settings.
