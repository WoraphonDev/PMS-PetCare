# T-0016-05 · May a managed account log in with its placeholder email?
- Status: open
- Raised by: claude · T-0016 (card review, Friday) · 2026-10-23
- Context:
  - §15 `#rule-managed-account-identity` stores `<user_id>@managed.invalid` as the managed account's email. `#rule-email-login-policy` exempts managed accounts from email verification only and forbids mailing `managed.invalid`. Neither section says whether login **by that address** is allowed.
  - Today `auth.login` (`apps/api/src/modules/identity/use-cases/auth.login.ts`) sends any identifier containing `@` to Better Auth's email sign-in. Global `requireEmailVerification` is off, and the pre-check exempts `isManaged`. So `<user_id>@managed.invalid` + the correct password **logs in** once T-0016 creates such accounts.
  - The user id is not secret: `StaffMember.userId` is returned by `GET /staff`. The password is still required, so this is a second identifier, not a bypass.
  - The earlier T-0016 card draft required "login with the placeholder email fails". That needs a change to `auth.login.ts`, which is outside the card's `allowed_paths`, so the draft has dropped it until this question is answered.
- Question: Should login with `<user_id>@managed.invalid` be rejected?
- Options:
  (A) Reject. In `auth.login`, an identifier that resolves to an `isManaged` user through an email (`@`) is refused like a wrong password: the same password hashing work, failure counter, `UNAUTHENTICATED`, no session or cookie. Managed accounts log in by username only. T-0016 then adds `apps/api/src/modules/identity/use-cases/auth.login.ts` and a login test (e.g. `apps/api/test/identity/managed-login.test.ts`) to `allowed_paths`, a spec line in `#rule-email-login-policy`, and the acceptance test "placeholder email login → `UNAUTHENTICATED`, no session". About 5–10 changed lines.
  (B) Allow as today. The placeholder is an internal alias that still needs the password. No code or spec change; T-0016 does not test it.
  (C) Reject, but in a separate card after T-0016 (T-0016 ships with today's behaviour).
  — แนะนำ: A. F09 says managed accounts sign in with username + password, and §14/§15 never show the placeholder to anyone; accepting it as a login name gives an extra identifier nobody is meant to use. The change is small, sits in the existing pre-check, and is cheapest to test together with the endpoint that creates managed accounts.
