# T-0010-01 · Better Auth twoFactor clock policy
- Status: answered
- Raised by: codex · T-0010 · 2026-10-20
- Context: T-0010 requires the existing Better Auth twoFactor plugin, TOTP generated with a test clock, and trusted-device expiry advanced with that clock. AGENTS.md rule 5 requires current time only from injected clock/now. Installed better-auth 1.7.11 twoFactor options have no clock or TOTP verification override. Its totp verifier delegates to @better-auth/utils createOTP.verify, which reads Date.now(); trust-device issuance and validation directly use Date.now()/new Date(). Adding CLOCK to createAuth cannot change these internal reads. A temporary real-Postgres characterization test on Node 24.22.0 passed: after plugin setup, a TOTP generated independently with node:crypto at 2001-01-01T00:00:00Z returned 401; one generated at system time returned 200. The probe was removed after execution; no application code was changed.
- Question: May T-0010 use the pinned plugin's internal system clock as a narrow exception, while all application-owned time and audit timestamps use injected CLOCK, and test plugin expiry/TOTP with Vitest's mocked Date rather than claiming that the plugin accepts the injected clock?
- Options: (A) Approve that narrow third-party clock exception for T-0010; use mocked Date only in isolated tests, never a production global Date override. (B) Keep strict injection for plugin internals; approve a separate integration/design card providing a supported clock-aware plugin before resuming T-0010. Recommendation: A, preserving the required existing plugin and no-new-dependency scope. No exception is assumed until explicitly approved.
- Answer: 2026-10-20 · User explicitly approved option A: pinned Better Auth internal system clock is permitted as a narrow third-party exception. Application-owned timestamps and audit use injected CLOCK; isolated tests mock Date; production global Date overrides are prohibited.
