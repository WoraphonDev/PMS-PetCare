# T-0013-01 · DELETE with a body but no Content-Type is rejected before routing, without `details.fields._`
- Status: open
- Raised by: claude · T-0013 · 2026-10-22
- Context: #contract-branch-schedule-common says GET/DELETE take no body: nonempty → `VALIDATION_FAILED` at `_`, absent/zero-byte accepted, "ไม่แก้ common guards เพื่อ enforce กติกานี้". Fastify 5 treats DELETE as a body method: with no `content-type` and any body framing (`content-length: 1` or `transfer-encoding: chunked`, even an empty chunked body) it has no parser for `''` and fails before the route handler. `apps/api/src/common/error.filter.ts` maps that to `400 VALIDATION_FAILED "Request rejected"` with **no** `details`. Measured on `DELETE /branches/{id}/closures/{closureId}`:
  - no content-type, `content-length: 1` → 400 `VALIDATION_FAILED` without `details.fields._` (spec wants `_`)
  - no content-type, empty chunked body → 400 (spec wants 204: zero-byte body accepted)
  - no content-type, empty JSON chunked body (`application/json`) → 400 (Fastify `FST_ERR_CTP_EMPTY_JSON_BODY`)
  With `text/plain` or a non-empty JSON body the request reaches the handler, and T-0013 handles it per the spec (covered by tests). GET is not affected because Fastify never parses a GET body; T-0013 now checks the GET bytes itself.
  Fixing the cases above needs a change in `apps/api/src/common/**` or `create-app.ts` (a catch-all content-type parser, or mapping Fastify body errors to `details.fields._`). Both are outside T-0013's `allowed_paths` and would change every body route, not only schedule.
- Question: Should the pre-routing DELETE cases follow the `_` / zero-byte rule, and if so where?
- Options:
  (ก) Accept the current behaviour for these edge cases: the status/code are still `400 VALIDATION_FAILED`, only `details.fields._` is missing, and empty-chunked DELETE without content-type is rejected. Record it as a known limitation in the spec.
  (ข) Separate small infra card (`apps/api/src/common/**`, `create-app.ts`): register a `''` content-type parser that buffers the raw body (bounded by `bodyLimit`) and have the Fastify-client-error branch of the error filter report `details.fields._` for body errors on bodyless routes; add the missing tests then.
  (ค) Widen T-0013's `allowed_paths` to `apps/api/src/common/error.filter.ts` and fix it here.
  — แนะนำ: (ข) — it is a cross-cutting HTTP concern that every future DELETE route shares, so it belongs in one infra card with its own tests, not in the schedule card; (ก) is acceptable meanwhile because the code/status already match.
