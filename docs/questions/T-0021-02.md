# T-0021-02 · Consumer retry and dead-letter policy
- Status: answered
- Raised by: claude · T-0021 (card preparation) · 2026-10-24
- Context:
  - ADR-0004: worker → queue (BullMQ/Valkey) → internal consumers and external webhooks; webhooks get "retry + dead-letter". Nothing fixes the number of attempts, the backoff, or where dead jobs live.
  - `outbox_event` has `published_at` and `attempts` only — no dead/failed status column. Adding one needs a spec + migration.
  - T-0021 relays each event to one job per subscribed consumer (`jobId = <consumer>.<eventId>` — revised 2026-10-24: BullMQ 6.4.1 rejects custom ids containing `:`). Relay-side failures (Valkey down) are retried by the poll loop with capped backoff; this question is about **consumer** failures.
  - Delivery is at least once. `jobId` dedup only works while the earlier job is retained, so how many completed jobs are kept sets the dedup window; consumers must be idempotent by `eventId` either way (T-0021 card).
  - No real consumer exists yet; the first ones (notification, Channel webhooks) come later and may want their own policy.
- Question: How many times is a failing consumer job retried, and what is the dead-letter set?
- Options:
  (A) **Default policy in BullMQ, overridable per consumer later:** 8 attempts, exponential backoff starting at 5 s (5, 10, 20 … 320 s — about 10.5 minutes in total). After the last attempt the job stays in BullMQ's **failed** set (`removeOnFail: false`) — that set *is* the dead-letter, `deadLetterCount` = its size. Completed jobs are trimmed to the last 1,000 (for debugging; also the window in which a re-relayed event is deduplicated by `jobId` — after trimming, a re-relay creates a new job and the idempotent consumer absorbs it). Failed jobs are never trimmed automatically, so the dead-letter set grows until someone handles it; `deadLetterCount > 0` raises a warning (T-0021-01). Replay is out of scope (a later card or a manual BullMQ action).
  (B) Same retries, but move dead jobs into a separate queue `outbox-dead` explicitly in a `failed` handler. Clearer name, but two places to look and an extra move that can itself fail.
  (C) Store dead events in Postgres (new table or a status column on `outbox_event`). Durable and queryable with SQL, but needs a spec amendment and a migration — not in this card.
  — แนะนำ: A. It uses what BullMQ already guarantees, needs no schema change, and a consumer with different needs (e.g. Channel webhooks retrying for hours) can pass its own attempts/backoff when its card arrives. Note: Valkey must run with persistence (AOF) and `maxmemory-policy noeviction` in staging/production so queued and failed jobs survive restarts and memory pressure — for T-0030/T-0032.
- Answer: 2026-10-24 · Zo chose (A) via Friday: 8 attempts, exponential backoff from 5 s; BullMQ's failed set (`removeOnFail: false`) is the dead-letter and `deadLetterCount` = its size; completed jobs retained to the last 1,000. `jobId` dedup only holds within that retained-job window; consumers must be idempotent by `eventId`. Per-consumer overrides come with each consumer's card; replay is out of scope. Card: T-0021.
