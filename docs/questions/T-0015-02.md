- Context: foundation#ep-staff.invite gives `{ email, role, branchIds }` · F02, F03, F05 · email · audit `staff.invited`. #tbl-invitation: `branch_ids uuid[]` "ว่างได้เมื่อ role เป็น owner/manager" and has no FK, so the use case validates the ids. - Question: What is the exact request/response and validation for `POST /staff/invitations`?
- Options:
  (A) Strict body per §11. `email`: trimmed, lower-cased, valid email, 1–254 chars; must not end with `@managed.invalid`. `role`: `staff_role` enum. `branchIds`: array of unique UUIDs. Branch roles need ≥ 1 → `BRANCH_REQUIRED`. Owner/manager must send `[]` (otherwise `VALIDATION_FAILED` at `branchIds`). Any id that is not a branch of this org → `VALIDATION_FAILED` at `branchIds` (a body field, not a path id). Inactive branches are allowed. Manager inviting `owner`/`manager` → `FORBIDDEN`. Email of an active member → `ALREADY_MEMBER`; a removed former member may be invited. Response **201** `Invitation = { id, email, role, branchIds, expiresAt, invitedByUserId, createdAt }` (no token, no hash). Audit `staff.invited`: `entity_type 'invitation'`, `entity_id` = new invitation id, `before null`, `after { email, role, branchIds, expiresAt }`. A re-invite (F03) also sets `revoked_at` on the old row in the same transaction, with no separate audit row.
  (B) Same as A, but owner/manager branch ids are silently stored as `[]` instead of rejected.
  (C) Same as A, but inactive branches are rejected with `VALIDATION_FAILED`.
  — แนะนำ: A. It keeps strict bodies (§11), never stores data that has no effect, and treats body ids as validation like other body fields. Email in the audit row is the work address of the invitee, which the owner needs to trace who was invited; there is no token in it.
