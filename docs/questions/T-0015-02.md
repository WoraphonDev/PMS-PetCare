# T-0015-02 · staff.invite wire contract and branch-id validation
- Status: open
- Raised by: claude · T-0015 (card preparation) · 2026-10-22 (revised after review 2026-10-22)
- Context:
  - foundation#ep-staff.invite gives `{ email, role, branchIds }` · F02, F03, F05 · email · audit `staff.invited`.
  - #tbl-invitation: `branch_ids uuid[]` "ว่างได้เมื่อ role เป็น owner/manager"; it has no FK, so the use case validates the ids.
  - #rule-F07: "id ของ org อื่น → `NOT_FOUND` เสมอ (ไม่ใช่ `FORBIDDEN`)". It does not exempt ids sent in a body.
  - Not defined:
    - status code and response body;
    - email normalisation (the column is citext);
    - what happens when an owner/manager is invited with branch ids;
    - duplicate ids; inactive branches;
    - the audit `before`/`after`;
    - whether a removed former member can be invited again.
  - ¹: a manager cannot act on owners/managers and cannot make anyone owner/manager. F03's re-invite revokes the old invitation as a side effect. If that old invitation is for `owner`/`manager`, a manager could revoke it this way although T-0015-07 forbids revoking it directly.
  - The `ALREADY_MEMBER` check needs user ids for an email. Identity has `lower(email)` lookups that run on a caller's transaction, but none is exported (see card: identity read API).
- Question: What is the exact request/response and validation for `POST /staff/invitations`?
- Options:
  (A) Strict body per §11.
    - `email`: trimmed, lower-cased, valid email, 1–254 chars; must not end with `@managed.invalid`.
    - `role`: the `staff_role` enum.
    - `branchIds`: array of unique, well-formed UUIDs; malformed or duplicate → `VALIDATION_FAILED` at `details.fields.branchIds`.
    - Branch roles need at least one id → `BRANCH_REQUIRED`. Owner/manager must send `[]`, otherwise `VALIDATION_FAILED` at `branchIds`.
    - A well-formed id that is not a branch under the current tenant → `NOT_FOUND` (F07), checked in phase 2 before any write, whether it does not exist or belongs to another org. The two cases are **not** told apart, and no cross-tenant query is made.
    - Inactive branches are allowed. Manager inviting `owner`/`manager` → `FORBIDDEN` (phase 1, from the request alone).
    - **Re-invite and ¹:** after locking the pending invitations for that email (phase 2 of the shared protocol in T-0015-03), if the caller is a manager and any of them has role `owner`/`manager` → `FORBIDDEN`. That invitation stays unchanged; no new row, no audit row, no email. This check runs before `ALREADY_MEMBER` and the seat count. Example: an owner invites X as `manager`, then a manager invites X as `front_desk` → `FORBIDDEN`.
    - Email of an active member of this org → `ALREADY_MEMBER`; a removed former member may be invited; no user with that email → invite.
    - Response **201** `Invitation = { id, email, role, branchIds, expiresAt, invitedByUserId, createdAt }`, with no token and no hash.
    - Audit `staff.invited`: `entity_type 'invitation'`, `entity_id` = new invitation id, `before null`, `after { email, role, branchIds, expiresAt }`.
    - A re-invite (F03) also sets `revoked_at` on the old row in the same transaction, with no separate audit row.
  (B) Same as A, but owner/manager branch ids are silently stored as `[]` instead of rejected.
  (C) Same as A, but inactive branches are rejected.
  (D) Same as A, but an unknown branch id → `VALIDATION_FAILED` at `branchIds`. **This needs human approval of an F07 exception for body ids first** (F07 says `NOT_FOUND` always), and the exception must say that cross-org ids also answer `VALIDATION_FAILED`, so that the response does not reveal whether the id exists elsewhere.
  — แนะนำ: A. It keeps strict bodies (§11), never stores data that has no effect, and follows F07 as written. The email in the audit row is the invitee's work address, which the owner needs to trace who was invited; the audit row holds no token.
