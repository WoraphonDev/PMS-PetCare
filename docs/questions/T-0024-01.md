# T-0024-01 · Where does the web app get the role → permission table?
- Status: open
- Raised by: claude · T-0024 (card preparation) · 2026-10-24
- Context:
  - The web needs the permission table for menus (T-0024) and for showing/hiding buttons: add branch (owner only), invite/edit staff (owner, manager; manager cannot manage owners/managers — footnote ¹), payment settings (owner), etc. The API always enforces; the UI only hides what would fail.
  - The table exists once, in `packages/domain/src/permissions.ts` (`can`, `isOrgWideRole`, `canManageMember`). `packages/domain` is pure: no I/O, imports no internal package (ADR-0002, Biome rule).
  - ADR-0002 rule 4: `apps/*-web` → `api-client` / `contracts` / `ui` only. So the web may not import `@app/domain` today.
  - Copying the table into the web risks drift that no test catches.
- Question: How should the web get the permission table?
- Options:
  (A) **Allow web apps to import `packages/domain`** — a one-line human amendment to ADR-0002 rule 4: `apps/*-web → api-client / contracts / ui / domain` (domain stays pure, so it is safe in the browser). T-0024 adds `@app/domain` as a workspace dependency of `apps/pms-web` and imports `can` / `canManageMember`. One source of truth, no copy.
  (B) **Move the table into `@app/contracts`** (contracts exports the grants; domain imports them). No ADR change, but a separate card that touches `packages/domain`, `packages/contracts` and the API's guards — must merge before T-0024.
  (C) **Copy into the web** (`apps/pms-web/src/lib/permissions.ts`) with a comment pointing to §2. No ADR or extra card; drift risk accepted, caught only by review.
  — แนะนำ: A. The rule exists to keep I/O and server code out of clients; pure domain rules (permissions now, price/time rules later) are exactly what clients should share. The ADR edit is a human PR, like the ADR-0003 amendment for T-0021-04.
