# T-0029-01 · Where does the Playwright E2E run?
- Status: answered
- Raised by: claude · T-0029 (card preparation) · 2026-10-24
- Context:
  - T-0029 starts Postgres, Valkey and Mailpit with Testcontainers, builds and starts the API and the web, and drives Chromium. One run takes minutes and needs Docker and a downloaded browser.
  - CI today runs `pnpm verify` (lint, typecheck, unit/integration tests). Agents must not change `.github/**` (AGENTS rule 2), so a CI job for E2E can only be added by a human.
  - `#accept-signup-verification` makes this flow a release gate for opening signup; deployment (T-0030/T-0032) is not decided yet.
- Question: Where should the E2E run, and who wires it?
- Options:
  (A) **Local + PR evidence now, CI job by a human later:** T-0029 delivers `pnpm --filter @app/e2e e2e`; the dev agent runs it and pastes the result in the PR; a human adds a separate CI workflow (e.g. on PRs that touch `apps/**` or `packages/**`, plus nightly on `main`) as a follow-up — at the latest with T-0032, where it becomes a gate before production deploys. `pnpm verify` stays fast.
  (B) **Human adds the CI job in the same PR:** T-0029's PR also changes `.github/workflows/**`, so a human must author or approve that part and merge it. E2E protects every PR from day one; the card is no longer agent-only.
  (C) **Run inside `pnpm verify`:** no workflow change, but every `pnpm verify` (local and CI) needs Docker + Chromium and takes minutes longer.
  — แนะนำ: A. It keeps agents inside their allowed paths, does not slow every PR, and the release gate is still enforced: signup is not opened until a human has seen a green E2E run (and later a CI job) on the release commit.
- Answer: 2026-10-24 · human chose (A) in chat: T-0029 runs locally (`pnpm --filter @app/e2e e2e`) and the dev agent pastes the result in the PR; a human adds a separate CI job later (at the latest with T-0032). `pnpm verify` does not run E2E. Signup is opened to real users only after a human has seen a green E2E run on the release commit.
