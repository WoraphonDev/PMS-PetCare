# T-0015-05 · invitation.accept contract (incl. verified email and locking)
- Status: open
- Raised by: claude · T-0015 (card preparation) · 2026-10-22 (revised after review 2026-10-22)
- Context:
  - foundation#ep-invitation.accept: `POST /invitations/accept`, auth "user (หรือสมัครใหม่ใน flow เดียวกัน)", `{ token }`, F03, audit `staff.joined`. Signup in the same flow is T-0015-06; this question covers logged-in users only.
  - F03 lists `INVITATION_INVALID` (expired/used/email mismatch) and `ALREADY_MEMBER`. F09: managed accounts cannot join another org.
  - `membership` is unique on (`org_id`, `user_id`), so a removed former member already has a row.
  - Verified email: `#rule-email-login-policy` refuses login for real-email accounts with `emailVerified = false`. But `AuthGuard` and the session resolver do not check `emailVerified`, so a session created before that gate (or by any future path) would pass. The email match in F03 means the most if that email has been proven.
  - The error registry (foundation#errors, `packages/contracts/src/errors.ts`) has `UNAUTHENTICATED` (401), `FORBIDDEN` (403), `INVITATION_INVALID` (410). No new code may be added.
  - Not defined:
    - the response body;
    - the error for unknown/malformed/revoked tokens;
    - whether `ALREADY_MEMBER` uses up the invitation;
    - what happens to a removed member;
    - the membership `display_name`;
    - whether a suspended org can be joined (F04);
    - the audit content and the locks.
- Question: What does accept require, check, write and return, and must the email be verified?
- Options:
  - Base contract (all options):
    - Session user (`AuthGuard`; the existing `PASSWORD_CHANGE_REQUIRED` and 2FA session rules apply), no `X-Org-Id`. Strict body `{ token }` (string, 1–200 chars).
    - One tenant transaction with locks in the shared order of T-0015-03 (subscription row → invitation row → membership row). Every check below runs after the locks, in that transaction, before any write.
    - Unknown, malformed, expired (`expires_at <= now`), accepted, revoked, email ≠ user email (case-insensitive), or managed user → `INVITATION_INVALID` (410).
    - Org suspended → `ORG_SUSPENDED`.
    - Active membership exists → `ALREADY_MEMBER` (409), invitation unchanged.
    - Removed membership → set `status = 'active'`, with role and branches from the invitation (old `membership_branch` rows replaced).
    - Otherwise insert the membership (`display_name = user.name`) and its `membership_branch` rows.
    - Set `accepted_at = now`.
    - Audit `staff.joined`: actor = user, `entity_type 'membership'`, `entity_id` = membership id, `before null` (or `{ status: 'removed' }` on re-join), `after { role, branchIds, invitationId }`.
    - Response **200** `{ orgId, membershipId, role, branchIds }`.
    - No `max_staff` comparison (T-0015-03).
  - Verified email (choose one):
    (V1) Required. The accept use case checks `user.emailVerified === true`, after the managed-account check, **before** taking any lock. `false` → `UNAUTHENTICATED` (401), consistent with `#rule-email-login-policy`, which treats an unverified real-email account as not signed in; nothing is written. The web sends the user to `/verify-email` recovery.
    (V2) Required, but `false` → `INVITATION_INVALID` (410): the same answer as any other reason the invitation cannot be used, revealing nothing about the account state. The web cannot tell the user to verify.
    (V3) Not checked at accept; rely on the login gate only.
  - Other variants:
    (B) Same base, but `ALREADY_MEMBER` marks the invitation accepted (used up).
    (C) Same base, but a removed former member gets `ALREADY_MEMBER` and must be restored by `staff.update` instead.
  — แนะนำ: base contract + V1. V1 closes the gap that `AuthGuard` leaves, using an existing code whose meaning (an unverified real-email account has no usable session) is already in the spec. V2 is the choice if the human prefers to reveal nothing. V3 leaves the email match unproven for old sessions. One generic `INVITATION_INVALID` for every unusable token avoids telling a caller which invitations exist. Re-joining keeps the single (org, user) row the unique constraint requires.
