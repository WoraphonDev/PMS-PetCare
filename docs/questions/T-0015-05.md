# T-0015-05 · invitation.accept contract
- Status: open
- Raised by: claude · T-0015 (card preparation) · 2026-10-22
- Context: foundation#ep-invitation.accept: `POST /invitations/accept`, auth "user (หรือสมัครใหม่ใน flow เดียวกัน)", `{ token }`, F03, audit `staff.joined`. F03 lists `INVITATION_INVALID` (expired/used/email mismatch) and `ALREADY_MEMBER`. F09: managed accounts cannot join another org. `membership` is unique on (`org_id`, `user_id`), so a removed former member already has a row. Not defined: response body, error for unknown/malformed/revoked tokens, whether `ALREADY_MEMBER` consumes the invitation, what happens to a removed member, the membership `display_name`, whether a suspended org can be joined (F04), and the audit content. Signup-in-flow is T-0015-06.
- Question: What does accept require, write and return?
- Options:
  (A) Session user (`AuthGuard`; existing `PASSWORD_CHANGE_REQUIRED` and 2FA session rules apply); no `X-Org-Id`. Strict body `{ token }` (string, 1–200 chars). In one tenant transaction: lock the invitation row; unknown, malformed, expired (`expires_at <= now`), accepted, revoked, email ≠ user email (case-insensitive), or managed user → `INVITATION_INVALID` (410). Org suspended → `ORG_SUSPENDED`. Active membership exists → `ALREADY_MEMBER` (409), invitation left unchanged. Removed membership → set `status = 'active'`, role and branches from the invitation (old `membership_branch` rows replaced). Otherwise insert membership (`display_name = user.name`) + `membership_branch` rows. Set `accepted_at = now`. Audit `staff.joined`: actor = user, `entity_type 'membership'`, `entity_id` = membership id, `before null` (or `{ status: 'removed' }` on re-join), `after { role, branchIds, invitationId }`. Response **200** `{ orgId, membershipId, role, branchIds }`.
  (B) Same as A, but `ALREADY_MEMBER` marks the invitation accepted (used up).
  (C) Same as A, but a removed former member gets `ALREADY_MEMBER` / must be restored by `staff.update` instead.
  — แนะนำ: A. One generic `INVITATION_INVALID` for every unusable token avoids telling a caller which invitations exist. Leaving the invitation untouched on `ALREADY_MEMBER` is harmless (it still expires). Re-joining keeps the single (org, user) row the unique constraint requires.
