# T-0012-02 · branch.create / branch.update wire contract and coordinates
- Status: open
- Raised by: claude · T-0012 · 2026-10-21
- Context: foundation#ep-branch.create / #ep-branch.update give no request fields, status code or response body; #ep-branch.update only excludes `promptpay_id`. foundation#tbl-branch: `name` unique per org (no length rule), `address`/`phone` nullable, `latitude`/`longitude` numeric(9,6) nullable, `timezone` = `Asia/Bangkok` only (F06), `is_active` default true. numeric(9,6) is returned by the DB driver as a string; the spec does not say whether the wire uses JSON numbers or decimal strings, nor ranges (±90/±180), nor whether lat/long must be set together. Whether `isActive` (deactivate a branch) and `timezone` are writable here is not stated. Branch `name` length: only signup's `branchName` 1–100 trimmed exists (#rule-signup-input). The response DTO for a branch would expose `promptpayId` unless excluded — PromptPay is owner-only to update but nothing says who may read it.
- Question: What are the exact request/response contracts for `POST /branches` and `PATCH /branches/{branchId}`?
- Options:
  (A) Create = `{ name, address?, phone?, latitude?, longitude? }`; Update = partial of the same + `isActive?`, at least one field. Strict keys (`promptpayId`, `timezone`, `orgId`, `id`, timestamps → `VALIDATION_FAILED`); `timezone` is always server-set `Asia/Bangkok`. `name` trimmed 1–100 (same as signup branchName); `address` ≤ 500, `phone` ≤ 100 trimmed, nullable clears with `null`. Coordinates are JSON numbers with ≤ 6 decimals, latitude −90..90, longitude −180..180, both-or-neither (null together); response returns them as numbers. Create → 201 Branch DTO; update → 200 Branch DTO. Branch DTO = `id, name, address, phone, latitude, longitude, timezone, promptpayId, isActive, createdAt, updatedAt` (no `orgId`).
  (B) Same as A but coordinates are decimal strings on the wire (exact numeric(9,6) round-trip, no float conversion).
  (C) Same as A but `isActive` not writable in this card (deactivation is a separate decision).
  — แนะนำ: A, with a decision on whether `promptpayId` appears in the Branch DTO for all `org.settings.read` roles (recommend: included, since it is shown on payment QR to customers anyway). Coordinate number-vs-string is the key choice; A is simpler for clients, B avoids float rounding.
