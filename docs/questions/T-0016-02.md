# T-0016-02 · How the managed account is created (identity rows, flags, one transaction)
- Status: open
- Raised by: claude · T-0016 (card preparation) · 2026-10-23
- Context:
  - #tbl-identity: when Better Auth needs a non-null email, a managed account stores `<user_id>@managed.invalid`, which is never mailed or shown. `is_managed = true`, `managed_by_org_id` required.
  - F09: the password set by owner/manager → `must_change_password = true`; the account belongs to the creating org.
  - #rule-email-login-policy: managed accounts are exempt only from real-email verification (`email_verified` stays false; it must not be set true to fake verification).
  - Signup already writes identity rows and tenant rows in one runtime-role transaction (#rule-signup-atomic); the runtime role has write access to the identity tables (no RLS).
  - The placeholder email needs the user id, which Better Auth's `signUpEmail` only returns after it has inserted the row with some email.
  - ADR-0002: only module `identity` writes identity tables; org must call an identity public function.
- Question: How are the identity rows created, and in which transaction?
- Options:
  (A) A new identity public function (e.g. `createManagedAccount(tx, …)`) that runs **on org's tenant transaction**:
    - generates the user id;
    - inserts `user` (`name` = displayName, `email = <id>@managed.invalid`, `username`, `email_verified = false`, `is_managed = true`, `managed_by_org_id` = org, `must_change_password = true`);
    - inserts the `account` row (`provider_id 'credential'`, `account_id` = user id) with the password hashed by the same hasher Better Auth uses (`auth.$context.password.hash`), so login works unchanged.
    No session is created, no email is sent. Membership, branches and audit follow in the same transaction; any failure rolls back the account too.
  (B) Call Better Auth `signUpEmail` with a temporary email on a savepoint (like signup), then update the email to `<id>@managed.invalid` and set the flags in the same transaction.
  — แนะนำ: A. It never creates a row with a misleading email, needs no Better Auth hooks (no verification or auto-sign-in side effects), and keeps every write in one commit. The implementation must reuse Better Auth's hasher, and a test must prove that the new account can log in with the username and gets `PASSWORD_CHANGE_REQUIRED` first.
