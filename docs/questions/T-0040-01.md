# T-0040-01 · Confirm the hook-based fix (not a `''` parser) and main's measured responses
- Status: open
- Raised by: claude · T-0040 · 2026-10-22 (from the review round 1 SPEC QUESTION)
- Context: The card asks to "register a content-type parser for requests without a content-type" and assumes two things. (1) An empty body parsed to `""` is accepted by `assertNoBody`. (2) POST/PUT routes would receive a string but keep their responses. Measured on main c384f6a / Fastify 5.12.7:
  - `addContentTypeParser('*')` is the only way to reach the `''` slot, and `getParser` falls back to it for **every unknown media type** too. A parser there would change unknown-type responses and send every POST/PUT/PATCH without content-type to the route's Zod pipe, which returns `details.fields`. Main rejects those before routing.
  - `assertNoBody` (read-only for this card) accepts `""` only when the content-type is `text/plain`, so a parser returning `""` would still reject the empty chunked DELETE the card wants accepted.
  - Main returns `400 VALIDATION_FAILED "Request rejected"` **without** `details` for an unknown content-type, an over-`bodyLimit` body, and POST/PUT bodies without content-type. The card expected `fields.body` for the unknown type. The tests lock in the measured response.
  Implemented instead (PR #43): the existing `onRequest` hook sets `content-type: text/plain` on a DELETE that has none. Fastify's built-in text parser buffers it within `bodyLimit`, and `assertNoBody` decides. All card outcomes are met; no other method or media type changes.
- Question: Is the DELETE-only header adjustment acceptable in place of the card's parser wording, with main's measured `"Request rejected"` responses (no `details`) locked in?
- Options:
  (ก) Accept as implemented (3 lines in `create-app.ts`, no new buffering code).
  (ข) A `'*'` parser that buffers only DELETE-without-content-type and, for everything else, re-raises a 415 shaped like Fastify's `FST_ERR_CTP_INVALID_MEDIA_TYPE`. It also returns `undefined` for an empty body (since `""` is rejected without text/plain). This takes ~25 lines of bounded buffering, and unknown-type rejections gain `connection: close`.
  (ค) Also change `assertNoBody` / `error.filter.ts` so a real `''` parser works as worded. That is outside `allowed_paths` and needs a card change.
  — แนะนำ: (ก) — smallest change, reuses Fastify's own bounded text parser, and leaves every other request path byte-for-byte as on main (locked by tests).
