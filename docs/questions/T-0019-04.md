# T-0019-04 · Which `org_id` does a `platform.org_viewed` audit row carry?
- Status: open
- Raised by: claude · T-0019 (card review, Friday) · 2026-10-23
- Context:
  - T-0019-03 (B), approved by the human: every platform detail read (`platform.org.get`) writes a new §6 action `platform.org_viewed`. That answer decided **that** detail reads are audited. It did not decide **which shop the row belongs to**. The agent filled that in as a default "to be confirmed at merge", and the §18 draft and T-0019 card stated it as settled. They now mark it pending.
  - `audit_log.org_id` decides who can see the row: RLS shows a shop's rows to that shop's owner in `GET /audit-logs` (§17), and hides rows with `org_id` null.
  - `platform.org_status_changed` (T-0019-02 A) and `platform.plan_changed` (T-0020) carry the target shop's `org_id`.
- Question: Should `platform.org_viewed` rows carry the target shop's `org_id` (visible to its owner) or `org_id` null (platform-only)?
- Options:
  (A) Target shop's `org_id`, written in that shop's tenant transaction like the other platform writes. The owner sees in their audit log when, and by which admin, their shop's detail was opened.
  (B) `org_id` null: a platform-level row written on the platform connection. Shop owners never see it; only platform tooling (none yet) could read it.
  — แนะนำ: A. It matches the other two platform actions and puts admin access in front of the shop that was accessed, which is the reason to audit reads at all. Choose B if admin views should stay internal (e.g. support work the shop is not told about).
