# T-0020-01 · platform.org.setPlan contract: plan rules, period, note, downgrade, audit
- Status: answered
- Raised by: claude · T-0020 (card preparation) · 2026-10-23
- Context:
  - foundation#ep-platform.org.set_plan: `PUT /platform/orgs/{orgId}/subscription` · platform admin · `{ planCode, currentPeriodEnd?, note? }` · audit `platform.plan_changed` · **human_review**.
  - #tbl-subscription: one row per org (`plan_id`, `started_at`, `current_period_end` null = no expiry, `note`). #tbl-plan: `code` unique, `is_active`.
  - #rule-branch-capacity: setPlan must lock the same subscription row as branch create (and, since §14, every staff writer). It also says an inactive plan or a past `current_period_end` is still enforced (no lifecycle in MVP).
  - T-0015-03: lowering a plan does not cancel pending invitations.
  - T-0019-02 decides whether platform audit rows carry the shop's `org_id` (visible to the owner).
  - Not defined:
    - PUT semantics for the optional fields;
    - unknown or inactive `planCode`;
    - past `currentPeriodEnd`;
    - whether `started_at` changes;
    - downgrading below current usage;
    - the no-op;
    - the response;
    - the audit content (incl. whether `note` is in it).
- Question: What does setPlan accept, write and return?
- Options:
  (A) Strict body:
    - `planCode` 1–50, must name an **active** plan (unknown or inactive → `VALIDATION_FAILED` at `planCode`);
    - `currentPeriodEnd`: ISO instant or null, **omitted = null** (PUT replaces), any instant allowed (past values are enforced as today);
    - `note`: trimmed 1–500 or null, omitted = null.
    In the org's tenant transaction:
    - lock the subscription row `FOR UPDATE`;
    - all three values equal → 200, nothing written;
    - otherwise update them; `started_at = now` only when the plan changes;
    - downgrading below current usage is allowed: existing branches, members and pending invitations stay, and new ones are blocked by F05;
    - audit `platform.plan_changed` with `before`/`after` = the changed fields among `{ planCode, currentPeriodEnd }`. **`note` is not audited**: it is the admin's internal remark, and the row may be visible to the owner (T-0019-02). A note-only change therefore writes no audit row.
    Response 200 = the platform org detail (T-0019-01).
  (B) Same as A, but `note` is audited like the other fields (`before`/`after` include it whenever it changes).
  (C) Same as A, but omitted optional fields keep their current values (PATCH-like).
  — แนะนำ: A. Plan and period changes affect billing and limits and are audited; the internal note is not shop-facing data. PUT replacing every field avoids "did omitting it clear it?" mistakes on a money-related endpoint. Choose B if every admin edit must be traceable, together with T-0019-02 (B) so notes stay out of the owner's audit view.
- Answer: 2026-10-23 · human chose (A) in chat: PUT replaces (omitted `currentPeriodEnd`/`note` = null); `planCode` must name an active plan; subscription row locked; no-op → 200; `started_at = now` only on a plan change; downgrade below usage allowed; audit only `planCode`/`currentPeriodEnd` changes, `note` never audited; 200 = detail. Spec: foundation#contract-platform-set-plan.
