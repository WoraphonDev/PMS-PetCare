# T-0017-04 · `staff.update`: branchIds sent for an owner/manager target without `role`
- Status: answered
- Raised by: claude · T-0017 (implementation) · 2026-10-23
- Context:
  - #contract-staff-update: "the resulting state must be valid … owner/manager have no branches". T-0017-01 (A): `branchIds` "as in invite", so `{ role: "owner" | "manager", branchIds: [x] }` is `VALIDATION_FAILED` at the body (step 2), as in #contract-staff-invite.
  - Not covered: `{ branchIds: [x] }` (no `role`) for a target that **is** owner/manager. The body alone is valid. Only after the target lock (step 3) is the resulting state known to be invalid. The error order (steps 4–7) names no code or step for it.
- Question: What does `PATCH /staff/{id}` answer for `{ branchIds: [non-empty] }` when the target's role is owner/manager and `role` is not sent?
- Options:
  (A) `VALIDATION_FAILED` with `details.fields.branchIds` (the invite rule applied to the resulting role), checked right after the manager rule (step 4) and before `BRANCH_REQUIRED` / branch `NOT_FOUND` (step 5). Nothing is written. No new code.
  (B) Ignore `branchIds` for org-wide roles: answer 200 and keep no branches (silently dropped).
  (C) Treat it as a no-op error-free 200 only when `branchIds` is `[]`; otherwise as (A).
  — แนะนำ: A. Same code and field as the invite rule, so clients get one rule for "owner/manager take no branches". It sits after the manager rule so a manager still gets `FORBIDDEN` first for an owner/manager target (no information leak). B hides a client bug. Note: `{ branchIds: [] }` for an owner/manager target is valid and a no-op under every option.
- Answer: 2026-10-23 · human chose (A) in chat: `VALIDATION_FAILED` with `details.fields.branchIds`, checked after the manager rule (step 4) and before `BRANCH_REQUIRED` / branch `NOT_FOUND` (step 5); nothing written.
