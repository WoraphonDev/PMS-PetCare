# T-0017-01 · staff.update wire contract, role/branch rules and error order
- Status: open
- Raised by: claude · T-0017 (card preparation) · 2026-10-23
- Context:
  - foundation#ep-staff.update: `PATCH /staff/{membershipId}` · `staff.update` · `{ role?, branchIds?, displayName? }` · F01, F02, ¹ · audit `staff.role_changed`.
  - F01: the last active owner cannot be demoted (`LAST_OWNER`). F02: branch roles need ≥ 1 branch (`BRANCH_REQUIRED`).
  - ¹: a manager cannot act on owners/managers and cannot make anyone owner/manager. §8: "manager ตั้งคนอื่นเป็น owner → `FORBIDDEN`".
  - §14 `#rule-staff-check-and-lock` lists T-0017 as a writer that takes lock 1 (subscription) and lock 3 (membership).
  - #contract-staff-invite fixes the role/branch-id rules for invitations (owner/manager `[]`, malformed id → `VALIDATION_FAILED`, unknown in tenant → `NOT_FOUND`).
  - T-0016-04 (open) decides whether managed accounts may hold owner/manager roles, which also limits promotion here.
  - Not defined:
    - the response;
    - PATCH no-op behaviour;
    - what happens to `branchIds` when the role moves between org-wide and branch roles;
    - whether `displayName` also changes `user.name`;
    - the caller acting on their own membership;
    - the error precedence.
- Question: What does `PATCH /staff/{membershipId}` accept, check (in order), write and return?
- Options:
  (A) Strict body per §11, at least one field:
    - `displayName` 1–100 trimmed (membership only; `user.name` unchanged, since one account can belong to several shops);
    - `role` from `staff_role`; `branchIds` as in invite (unique UUIDs).
    - The resulting state must be valid: branch role → ≥ 1 branch (`BRANCH_REQUIRED`); owner/manager → no branches. Changing to owner/manager without `branchIds` clears them; changing to a branch role from owner/manager requires `branchIds`.
    - Check order:
      1. guards;
      2. body / id → `VALIDATION_FAILED`;
      3. phase 2: lock subscription (missing → `INTERNAL`), re-read org status → `ORG_SUSPENDED`, lock the target membership — absent, other org or `removed` → `NOT_FOUND`;
      4. manager caller and (target is owner/manager, or new role is owner/manager) → `FORBIDDEN` (also for a manager's own membership);
      5. resulting branch role without branches → `BRANCH_REQUIRED`; branch ids not in the tenant → `NOT_FOUND`;
      6. demoting the last active owner (incl. the caller) → `LAST_OWNER`;
      7. the T-0016-04 rule for managed accounts.
    - A no-op (all values equal) → 200, nothing written.
    - Write: membership role/`display_name`/`updated_at` and `membership_branch` rows, plus the audit (T-0017-03), in one transaction.
    - Response **200** `StaffMember` (the #contract-staff-list shape).
  (B) Same as A, but `displayName` also updates `user.name`.
  (C) Same as A, but the caller may never change their own role (`FORBIDDEN`), even an owner with other owners present.
  — แนะนำ: A. It reuses the §14 locks and the invite rules, and keeps `user.name` per account, not per shop. F01 already protects the last owner, so owners stepping down when another owner exists needs no extra rule.
