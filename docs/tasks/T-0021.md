# T-0021 · Outbox relay worker

> Drafted by an agent at the human's request; revised 2026-10-24 after two review rounds. Decisions T-0021-01 … T-0021-04 are **answered (A)** by Zo via Friday on 2026-10-24. **Gate: implementation starts only after a human has merged (1) the ADR-0003 amendment for T-0021-04 (decision PR) and (2) this card.** The technical defaults below are confirmed by the human on merge; they add no table, column, error code, endpoint, permission, audit action or business rule. A dev agent must not edit this card.

## Goal

The `worker` process (ADR-0002) moves committed `outbox_event` rows into a BullMQ queue on Valkey and marks them published, so every consumer that subscribes to an event's type **at the moment the event is relayed** gets it **at least once** after the writing transaction commits (ADR-0004). Consumers added later get no backlog of events already relayed (T-0021-03). Consumer jobs that keep failing end in a dead-letter set, and the worker reports how far behind the outbox is. A Valkey outage never holds database locks open indefinitely and never blocks shutdown.

## Design (technical defaults confirmed by the human on merge; decisions per T-0021-01 … 04 = A)

### Envelope

Each job carries `OutboxEnvelope`, built only from the row's columns (ADR-0004 §3):
`{ eventId, type, orgId, branchId, aggregateType, aggregateId, aggregateVersion, occurredAt (ISO), payload }`.

### Delivery guarantee and consumer idempotency

- Delivery is **at least once for the consumers subscribed when the event is relayed** (the registry at relay time decides the fan-out). Nothing is promised retroactively to a consumer added later (see "no subscriber" below). The same event can reach a subscribed consumer more than once, for example: the relay added the jobs, then crashed or timed out before its DB commit; or a Valkey command timed out on our side but was applied on the server.
- `jobId` dedup (below) only suppresses a duplicate **while the earlier job is still retained** in Valkey (waiting, active, delayed, failed, or completed and not yet trimmed). Once a completed job has been removed (`removeOnComplete` trimming), adding the same `jobId` creates a **new** job.
- Therefore **every consumer must be idempotent by `eventId`** and must order or drop stale events by `aggregateVersion` (never assume it is contiguous — #rule-branch-version). This is part of the `OutboxConsumer` contract (doc comment on the type) and of every future consumer card. This card adds **no** durable dedup table or schema.

### Consumer registry

- `OutboxConsumer = { name: string; types: readonly string[]; handle(envelope): Promise<void> }`, registered in one list in `apps/api/src/outbox/consumers.ts` (one entry per line, alphabetical by `name`). **The list is empty in this card**; tests register their own consumers.
- **Consumer name format:** `^[a-z][a-z0-9-]{0,39}$` (lowercase, digits, hyphen; no `:` or `.`). Names are **unique**. The registry is validated when the worker starts; an invalid or duplicate name, or an empty `types`, throws and the worker refuses to start.
- **Job id:** `"<consumer>.<eventId>"` — deterministic and with no colon. BullMQ 6.4.1 throws `Custom Id cannot contain :` for a custom id containing `:` unless it has exactly three `:`-separated parts (`dist/cjs/classes/job.js`, `Job.validateOptions`), so the earlier draft's `"<consumer>:<eventId>"` is invalid. The `.` separator is unambiguous because names cannot contain `.` and `eventId` is a uuid.
- Fan-out happens in the relay: one job per (event, subscribed consumer) on the single queue `outbox`, job name = consumer name.
- **No subscriber (T-0021-03 A):** an event whose type has no subscribed consumer **when it is relayed** is marked published without a job. Cut-off:
  - an event already relayed and marked published while it had no subscriber is **never** sent to a consumer added later;
  - a row still **pending** (not yet relayed) when a new consumer is deployed may be delivered to that consumer — so a new consumer can receive some events written before its deploy, but must not rely on getting all of them;
  - a later consumer initialises from current data (the owner module's public read) or a future replay tool. Every future consumer card must state this.

### Connections (producer vs worker)

Each Redis client is created by the outbox module from `VALKEY_URL` and closed by it. They are separate from the `iovalkey` client used for rate limits.

- **Producer** (the `Queue` used by the relay and by the lag report): `maxRetriesPerRequest: 1`, `enableOfflineQueue: false`, `commandTimeout: 2000` ms, `connectTimeout: 2000` ms, reconnect with capped backoff (≤ 2 s). With Valkey down, `addBulk` fails fast instead of queueing commands in memory.
- **Worker** (the BullMQ `Worker`'s connections): `maxRetriesPerRequest: null` (BullMQ requires this for blocking connections — `redis-connection.js` warns otherwise) and the default offline queue; it reconnects indefinitely and resumes processing on its own.

### Relay loop (in the worker)

- Every poll (1 s; immediately again while a full batch was returned), on the **platform connection** in one transaction that starts with `SET LOCAL idle_in_transaction_session_timeout = '10s'` and `SET LOCAL lock_timeout = '2s'`:
  1. `select … from outbox_event where published_at is null order by occurred_at, id limit 100 for update skip locked` — several worker replicas never relay the same row at the same time;
  2. add the jobs for **the whole claimed batch** — every row × every subscribed consumer — in one `queue.addBulk` under **one enqueue deadline of 5 s for the entire fan-out** (a timer that rejects; the client's own timeouts normally fire first). The deadline is started once per batch and **never restarted per row or per consumer**; if the fan-out of the batch is split into several calls, they all share the same deadline;
  3. set `published_at = clock.now()` on the rows whose jobs were added; commit.
- The row locks are therefore held for at most the enqueue deadline plus a few statements — never for as long as Valkey is down.
- If adding jobs fails or the deadline passes: roll back, then in a separate short platform transaction `attempts = attempts + 1` for those rows, log a warning (event ids and types only — never the payload), and retry on a later poll with capped backoff (1 s doubling to 30 s while failures continue; reset on success). Rows are never skipped or dropped. A timed-out `addBulk` may still land later; that is covered by the at-least-once rule above.
- `published_at` comes from the injected `Clock`, never `now()` in SQL.
- **Audit (T-0021-04 A, ADR-0003 amendment):** the relay's updates of `published_at` and `attempts` are outbox delivery bookkeeping and write **no** `audit_log` row. The exemption covers only these two columns; any other platform write keeps the ADR-0003 rule. No audit action is added.

### Consumer worker and dead-letter

- One BullMQ `Worker` on `outbox` dispatches by job name to the registered consumer. An unknown job name (consumer removed after enqueue) fails the job without retry (`UnrecoverableError`), so it lands in the dead-letter set and the worker keeps running.
- **Retry and dead-letter (T-0021-02 A):** default job options `attempts: 8`, `backoff: { type: "exponential", delay: 5000 }` (5, 10, 20 … 320 s ≈ 10.5 min), `removeOnFail: false` — BullMQ's **failed set is the dead-letter** and `deadLetterCount` = its size — and `removeOnComplete: { count: 1000 }`. The retained completed jobs are the dedup window described above. A per-consumer override is left to each consumer's card; replaying dead jobs is out of scope.

### Lag report

- **T-0021-01 A:** every 60 s the worker writes one JSON line to stdout: `{"msg":"outbox.lag","pendingCount":…,"oldestPendingAgeSeconds":…,"deadLetterCount":…}` — `oldestPendingAgeSeconds` = `clock.now()` − oldest pending `occurred_at` (0 when none).
- It also writes a `warn` line when `oldestPendingAgeSeconds ≥ 300` or `deadLetterCount > 0`.
- If Valkey is unreachable, the line still carries the DB values with `deadLetterCount: null`, plus a warning; it never throws out of the timer. No payload, ids of people or secrets in these lines. No metrics dependency or endpoint.

### Ownership and shutdown

The outbox module owns, creates and closes: the poll timer, the lag-report timer, the producer `Queue` (+ its client), the `Worker` (+ its clients) and the platform DB pool it opens. Nothing is created at import time.

The process bootstrap lives in one exported function in `apps/api/src/outbox/` (e.g. `startWorker({ consumers })`): it boots the Nest context, registers the signal handlers through `waitForShutdown`, and writes one readiness line `{"msg":"worker.ready"}` to stdout (and `process.send({ type: "worker.ready" })` when an IPC channel exists) once the relay, worker and lag timers are running. The readiness line has no URL, credential or payload. `worker.ts` calls it with the production registry; the child-process test calls the same function from a test entry with a test consumer, so the test exercises the real shutdown path.

On SIGTERM/SIGINT (via `waitForShutdown`), in this order, with an **overall deadline of 10 s**:

1. stop both timers (no new poll starts);
2. wait for the in-flight relay transaction to finish (it is itself bounded by the enqueue deadline);
3. `worker.close()` (waits for running jobs), then `queue.close()`;
4. if Valkey is unreachable and a close does not resolve, `disconnect()` the clients instead of waiting;
5. end the DB pool.

If the deadline passes, log which step did not finish and force-close the rest. The process exits by itself — no open handles.

### Deployment follow-ups (not in this card)

Recorded for T-0030/T-0032, no deployment file is touched here:

- Valkey must persist (AOF) and run with `maxmemory-policy noeviction` (BullMQ warns on any other policy); otherwise queued or dead-lettered jobs can disappear.
- Queue-loss recovery: if Valkey data is lost after rows were marked published, those events are not re-sent automatically. A replay tool (re-relay rows by `published_at` range) is a follow-up card; consumers being idempotent makes such a replay safe.

Out of scope: real consumers (notification, LINE, Channel webhooks), replaying dead-lettered jobs, the queue-loss replay tool, purging published rows (retention), a durable dedup table, a metrics server, alerting setup, any API endpoint, UI, deployment files.

## Tests (write first)

Integration tests on real Postgres + real Valkey (Testcontainers, `createTestInfra`) with **real BullMQ `Queue`/`Worker`** objects, fixed clock. Put them in `apps/api/test/outbox/`. Every test that waits on async work has an explicit deadline (`vi.waitFor` timeout or per-test timeout), never an unbounded wait.

- **Job id / registry:**
  - through a real `Queue`, `addBulk` with ids `"<consumer>.<eventId>"` succeeds and `queue.getJob(id)` returns the job; a regression test shows the old `"<consumer>:<eventId>"` form is rejected by BullMQ;
  - registry validation: invalid name (uppercase, `:`, `.`, too long), duplicate name, empty `types` → worker start throws.
- **Relay:**
  - an event appended by a committed `withTenant` transaction is relayed: one job per subscribed consumer with the exact envelope and job id; the row gets `published_at` = clock time;
  - an event from a rolled-back writing transaction never appears;
  - no subscriber (T-0021-03 A): relayed with no subscriber → published, no job; register a consumer for that type afterwards → the already-published event is **not** sent to it;
  - pending cut-off: an event appended while no relay ran, then a consumer registered, then `relayOnce` → the new consumer **does** get it (pending rows are fanned out to the registry at relay time);
  - order: three events with different `occurred_at` are added in `occurred_at` order;
  - batch: 250 pending rows → all published over successive `relayOnce` calls, each at most 100;
  - two relays running in parallel publish every row exactly once and no row is relayed by both (skip locked).
- **At-least-once / dedup:**
  - crash after `addBulk` but before commit (inject a throw) → the row stays unpublished; the next run publishes it, and while the first job is retained Valkey still holds exactly one job per id;
  - same, but the first job was processed and then removed (simulate trimming with `job.remove()` / `queue.clean`) → the next run creates a **second** job with the same id and the consumer is called twice — the test asserts this documented behaviour;
  - a test consumer that is idempotent by `eventId` produces one effect in both cases (pattern later consumers follow).
- **Outage / recovery:**
  - Valkey stopped before a poll → `relayOnce` fails within the enqueue deadline (assert < 6 s), the transaction is rolled back, row locks are released (a parallel `select … for update nowait` on the row succeeds right after), `attempts` +1, warning logged without payload;
  - Valkey stopped **during** enqueue (pause/stop the container between claim and `addBulk`) → same result, no hang;
  - **batch deadline:** 100 pending rows × 2 subscribed consumers with Valkey writes paused (`CLIENT PAUSE 8000 WRITE`) → `relayOnce` rejects within 6 s **in total** (the 5 s deadline covers the whole fan-out, not each row), all 100 rows rolled back and `attempts` +1 each;
  - Valkey restarted → the next poll publishes the rows; the consumer worker reconnects and processes them without a restart;
  - producer client is configured with offline queue disabled and finite retries (assert the options).
- **Consumer worker / dead-letter** (test consumers):
  - success → job completed, handler called once with the envelope;
  - handler fails twice then succeeds → three attempts, backoff `exponential` 5000 ms in the job options (assert the production default job options; to keep the test fast, the relay takes its default job options as a constructor parameter — production passes the constants above, the test passes a 50 ms delay);
  - handler always fails → after attempt 8 the job is in BullMQ's failed set (`removeOnFail: false`) and `deadLetterCount` = 1;
  - completed jobs: after 1,005 completed jobs, 1,000 are retained (`removeOnComplete: { count: 1000 }`);
  - unknown job name → fails once into dead-letter, worker keeps running.
- **Lag report:** `pendingCount` / `oldestPendingAgeSeconds` / `deadLetterCount` with the fixed clock (0 when empty), exact JSON line `outbox.lag` every 60 s (fake timers), `warn` at `oldestPendingAgeSeconds` = 300 (and not at 299) and at `deadLetterCount` = 1, no payload or PII; with Valkey down it logs `deadLetterCount: null` and does not throw.
- **Shutdown:**
  - normal: close stops polling and closes queue, worker and pool; no open handles afterwards;
  - **SIGTERM while Valkey is unreachable**: shutdown completes within the 10 s deadline (assert), clients disconnected, pool ended;
  - SIGTERM during an in-flight relay: the relay finishes or rolls back, then shutdown completes.
- **Boundary:** the relay uses only the platform connection; the runtime role still cannot SELECT/UPDATE `outbox_event` (existing grants test keeps passing).
- **Audit (T-0021-04 A):** after relaying, failing (`attempts` +1) and recovering, `audit_log` has no new row (count before = after); no new audit action exists in code.
- **Real worker process (acceptance)** — `apps/api/test/outbox/worker-process.test.ts`, real Postgres + Valkey from `createTestInfra`:
  - `beforeAll` bundles **fresh** entries with tsdown into a temporary directory (never reuses `apps/api/dist`): the real `src/worker.ts`, and a test entry `apps/api/test/outbox/fixtures/worker-entry.ts` that calls the same `startWorker` with one test consumer subscribed to `branch.created`;
  - spawns `node <tmp>/<entry>.js` as a child process with the test DB/Valkey env (`DATABASE_URL`, `DATABASE_PLATFORM_URL`, `VALKEY_URL`, …) and an IPC channel; waits for `worker.ready` with a deadline; asserts stdout/stderr never contain the DB/Valkey URLs, `BETTER_AUTH_SECRET` or an event payload;
  - **SIGTERM while Valkey is disconnected** (real `worker.ts` entry): stop the Valkey container, then `child.kill("SIGTERM")` → the child **exits by itself** with code 0 within **12 s** (10 s shutdown deadline + margin); pending rows are still unpublished;
  - **SIGTERM with a relay in flight** (test entry): append a `branch.created` event, block the enqueue by running `CLIENT PAUSE 3000 WRITE` on Valkey, wait until the child has claimed the row (a parallel `select … for update nowait` on it fails), send SIGTERM → the relay finishes inside its 5 s enqueue deadline and commits, the row has `published_at` set and exactly one job exists, then the child exits by itself with code 0 within 12 s;
  - **SIGTERM with a relay in flight past the deadline** (test entry): same, but `CLIENT PAUSE 8000 WRITE` → the enqueue deadline fires, the transaction rolls back, the row is unpublished with `attempts` = 1, then the child exits by itself with code 0 within 12 s;
  - the parent kills the child with SIGKILL **only** in `afterEach` cleanup when a test already failed or timed out; a SIGKILL never counts as a passing shutdown, and every passing case asserts the exit came from the child (`exitCode === 0`, `signalCode === null`).
