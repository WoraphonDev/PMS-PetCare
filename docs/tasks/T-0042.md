# T-0042 · Invitation accept API (logged-in users)

> Drafted by an agent at the human's request; split out of T-0015 with human approval on 2026-10-22 (T-0015-05 base contract + V1). **Do not start implementation until a human has merged this card together with foundation §14, and T-0015 is merged.** A dev agent must not edit this card.

## Goal

A person who already has an account, is logged in, and has the invited email verified accepts an invitation and becomes an active member of the shop, or becomes active again after being removed. The seat reserved by the invitation becomes an active membership under the shared check-and-lock protocol. This card also holds every race test between accept and the T-0015 operations.

People without an account are out of scope (`#rule-invite-signup-followup`). `auth.signup` must not be used as a workaround.

## Contract (summary of `#contract-invitation-accept` — the spec text wins)

- `POST /invitations/accept`; logged-in user, no `X-Org-Id`; strict body `{ token }` (string 1–200).
- Check order (the first failing check answers):
  - Phase 1 (no lock, no write):
    1. guards → `UNAUTHENTICATED` / `PASSWORD_CHANGE_REQUIRED`;
    2. body → `VALIDATION_FAILED`;
    3. malformed token → `INVITATION_INVALID`;
    4. managed user → `INVITATION_INVALID`;
    5. `emailVerified = false` → `UNAUTHENTICATED`;
    6. tenant preflight in `withTenant(orgId)`, an unlocked read by hash: not found (incl. an org that does not exist), accepted, revoked, expired (`expires_at <= now`) or email mismatch (case-insensitive) → `INVITATION_INVALID`;
    7. org suspended → `ORG_SUSPENDED`.
  - Phase 2 (same transaction):
    8. lock subscription; a missing row → `INTERNAL` (fail closed, never `INVITATION_INVALID`);
    9. lock the invitation and re-check step 6 → `INVITATION_INVALID`;
    10. re-read `organization.status` → `ORG_SUSPENDED`;
    11. lock the membership; `active` → `ALREADY_MEMBER`, invitation untouched;
    12. write.
- Write:
  - new membership (`display_name = user.name`) + `membership_branch` rows, **or** reactivate a `removed` membership (role and branches replaced from the invitation, `display_name` kept);
  - `accepted_at = now`;
  - audit `staff.joined` (`before` null or `{ status: 'removed' }`, `after { role, branchIds, invitationId }`).
  No `max_staff` comparison, no outbox.
- Response 200 `{ orgId, membershipId, role, branchIds }`. The token is never returned, audited or logged.

## Tests (write first)

Integration tests run on real Postgres with real invitations created through T-0015's `POST /staff/invitations` (or its repository), with no mock repositories. Every error assertion checks status, envelope code, and that nothing was written (membership, `membership_branch`, invitation `accepted_at`, audit rows).

- **Contracts** — `packages/contracts/src/org/invitation.accept.contracts.test.ts`: strict body, missing/extra keys, wrong types, length limits.
- **`apps/api/test/org/invitation.accept.test.ts`:**
  - happy path, new member:
    - membership `active` with the invitation's role and branches, `display_name = user.name`, `accepted_at = now` (fixed clock);
    - one `staff.joined` audit row (actor = user);
    - 200 body as §14;
    - `me.get` shows the membership; works without `X-Org-Id`.
  - re-join: a `removed` membership becomes `active` with the invitation's role and branches (old `membership_branch` rows replaced) and its `display_name` kept; audit `before { status: 'removed' }`.
  - one test per check-order step:
    - guards; body;
    - malformed token; managed user;
    - **unverified email** (real-email user with `email_verified = false`, seeded directly): `UNAUTHENTICATED`, nothing written, and the response comes back **while another transaction holds the org's subscription lock** (it never waits on a tenant lock). The same no-wait assertion applies to a malformed token and a managed user.
    - unknown token; **well-formed token whose org id does not exist** → `INVITATION_INVALID` (not `INTERNAL`);
    - accepted; revoked; replaced by a re-invite; expired at exactly `expires_at` and after; email mismatch (a case-only difference is a match);
    - suspended org → `ORG_SUSPENDED`;
    - **missing subscription** for an existing org with a matching pending invitation (deleted through the platform connection) → `INTERNAL`, nothing written, no token in the log;
    - `ALREADY_MEMBER` with the invitation left unchanged (it can still be revoked).
  - suspension between the phases: hold the subscription lock in another transaction, start an accept (it waits at step 8), suspend the org and release the lock → `ORG_SUSPENDED` from step 10, and nothing is written.
  - the token never appears in responses, audit rows or captured logs (pino stream + `Logger.prototype` + `console`, as in T-0014). This does not show that proxies or browsers keep it private; the fragment link is that control.
- **Races** — `apps/api/test/org/invitation.races.test.ts`. Repeat each case enough times to hit both orders.
  - **invite vs accept:** accept turns pending X into active, so the count does not change.
    - At `max_staff` (X included), a parallel invite of a new email is always `PLAN_LIMIT_REACHED` and the accept succeeds.
    - At `max_staff − 1`, the invite always succeeds.
    - Afterwards active + pending ≤ `max_staff`.
  - **re-invite vs accept** (same email), one of two outcomes:
    - accept wins → membership active, re-invite → `ALREADY_MEMBER`, no new invitation;
    - re-invite wins → old invitation revoked, accept → `INVITATION_INVALID`, no membership, the new invitation pending.
    Never both a new membership and a new pending invitation.
  - **revoke vs accept**, one of two outcomes:
    - revoke wins → 204, accept → `INVITATION_INVALID`, no membership;
    - accept wins → membership active, revoke → `NOT_FOUND`.
    No membership from a token whose revoke committed first.
  - **double accept** of one token: one 200 and one `INVITATION_INVALID`; one membership row; one `staff.joined` audit row.
