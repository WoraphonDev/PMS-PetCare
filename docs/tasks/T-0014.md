# T-0014 · Branch payment settings (PromptPay ID) API

> PROPOSED: drafted by an agent at the human's request for human approval. Not executable until this card is human-merged **and** questions T-0014-01…04 are answered with authoritative spec text merged into `docs/spec/features/foundation.md`. A dev agent must not edit this card.

## Goal

The owner can set, replace or clear a branch's PromptPay ID through `branch.paymentSettings.update`, validated by F08, written atomically with a version bump and an audit row, with no outbox event. This is the shop's receiving account for customer payments, so the card is `human_review: true`.

## Contract (spec-fixed vs pending)

Fixed by the spec today:

- `PUT /branches/{branchId}/payment-settings`, `@RequirePermission("branch.payment_settings.update")` (owner only; manager and branch roles → `FORBIDDEN`).
- F08: mobile `^0\d{9}$` or 13-digit tax ID with valid checksum; otherwise `VALIDATION_FAILED` with `details.fields.promptpayId`.
- `branchId` not a UUID → `VALIDATION_FAILED`; absent or other-org branch → `NOT_FOUND` (F07). Suspended org → `ORG_SUSPENDED` (F04). `PASSWORD_CHANGE_REQUIRED` (F09) and `UNAUTHENTICATED` from the existing guards.
- Version: the same `UPDATE` sets `version = version + 1` and reads it from `RETURNING` (#rule-branch-version), on the row locked with `lockBranch`.
- Audit `branch.payment_settings_updated` in the same transaction (§6). **No outbox event** (#rule-branch-version: "update ที่ไม่มี event เช่น PromptPay").

Pending human answers (recommendation in brackets — implement only what is merged):

- T-0014-01 request/response — [strict `{ promptpayId }` required, string after trim or `null` to clear; 200 `Branch` DTO].
- T-0014-02 checksum — [Thai 13-digit mod-11 check digit, any first digit, trim only, no dash stripping].
- T-0014-03 no-op — [equal value → 200 current DTO, no UPDATE/version/audit; change also sets `updated_at = ctx.now`].
- T-0014-04 audit content — [`entity_type 'branch'`, `entity_id` = branch id, `before/after = { promptpayId }` full values].

Not in scope (do not add): re-authentication or 2FA for this endpoint, extra rules for `is_active = false` branches, PromptPay QR payload generation (module `sales`), UI (`scr-settings-branch` payment tab is T-0025), any new error code, permission, audit action, outbox event, column or migration.

## Tests (write first)

Integration tests on real Postgres through the existing harness (`apps/api/test/org/support.ts`); no mock repositories. Every error assertion checks status, envelope code, `details.fields` where relevant, and that nothing was written (branch row, version, audit).

- `packages/contracts/src/org/branch.payment_settings.contracts.test.ts`: valid mobile; valid 13-digit IDs (incl. leading `0` juristic ID) and one wrong check digit per position class; 9/11-digit mobile, mobile not starting with `0`, 12/14 digits, non-digits, dashes/spaces per T-0014-02, empty after trim, `null` per T-0014-01; missing key, extra keys (`version`, `name`, `orgId`, …), non-object/array/number bodies.
- `apps/api/test/org/branch.payment_settings.update.test.ts`:
  - happy path: owner sets mobile, replaces with tax ID, clears (if T-0014-01 allows `null`); response body per T-0014-01; DB row and `branch.list` show the new `promptpayId`; `version` +1 and `updated_at = ctx.now` (fixed clock).
  - no-op per T-0014-03: no version bump, no audit.
  - audit: exactly one `branch.payment_settings_updated` row per effective change with the content of T-0014-04, `actor_user_id` = caller, `occurred_at = ctx.now`; **no `outbox_event` row** of any type.
  - atomicity: force the audit insert to fail after the UPDATE → `INTERNAL`, branch value and version unchanged.
  - roles: `manager`, `front_desk`, `groomer`, `caretaker` → `FORBIDDEN` (manager is the key case: it has `branch.update` but not this permission).
  - every endpoint error via `expectGuardErrors` (`UNAUTHENTICATED`, org header `VALIDATION_FAILED`/`FORBIDDEN`, `PASSWORD_CHANGE_REQUIRED`) + `ORG_SUSPENDED` on a suspended org + `VALIDATION_FAILED` for malformed `branchId` and each F08 failure.
  - other organization's branch id → `NOT_FOUND`; unknown branch id → `NOT_FOUND`.
  - concurrency: parallel payment PUT and `branch.update` on the same branch both succeed with distinct consecutive versions; the `branch.updated` event payload still has no `promptpayId` and its `changedFields` never lists it.
  - regression: `branch.update` with `promptpayId` still → `VALIDATION_FAILED`; no PromptPay value appears in any response error message or app log line.
