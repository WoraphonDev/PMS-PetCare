# T-0038 · `branch.version` column

## Goal

Add the per-aggregate version column that T-0012 (and later T-0014) uses for outbox `aggregate_version`, as approved in T-0012-05 option C. Schema only — no API, no increments in application code, no outbox writes.

## Read first (only the cited sections)

- `docs/spec/features/foundation.md#tbl-branch`, `#rule-branch-version`, `#rule-branch-outbox`, `#tbl-outbox_event`
- `docs/spec/01-conventions.md` (Database)
- `docs/adr/0003-multi-tenancy.md`, `docs/adr/0004-channel-api.md` (outbox §3)
- Existing `packages/db/src/schema/org/branch.ts`, `packages/db/test/org-tables.test.ts`, `packages/db/test/support/**` as precedents

## Deliverables

- `branch.ts`: `version: integer().notNull().default(1)` + check `branch_version_positive` (`version >= 1`); keep existing columns/constraints unchanged.
- One new migration generated with `pnpm --filter @app/db generate` (next free number after the latest merged migration; never edit merged migrations or hand-merge `meta/`). Existing rows get `1` through the column default in the same `ALTER TABLE`.
- No DB trigger (application-owned increment per `#rule-branch-version`; if the human chooses the trigger alternative in `#org-branch-technical-gates` item 4 before this card starts, that choice must be written into the card by a human first). No grants, RLS, enum, or other table changes.

## Tests (write first) — `packages/db/test/branch-version.test.ts`, real Postgres

- Migrated schema: `version` is `integer not null default 1` (catalog check). Backfill: a branch row inserted before the new migration is applied has `version = 1` afterwards — if the existing harness cannot apply migrations stepwise, write a question instead of changing `test/support/**`.
- Insert without `version` → `1`; `version = 0` or negative → check violation; `null` → not-null violation.
- As `app_runtime` with tenant context: `update branch set version = version + 1 … returning version` returns `2`; under RLS another org's branch is not updated (0 rows).
- Two concurrent transactions each `version = version + 1` on the same row → committed values are `2` and `3` (second waits on the row lock); final `3`.
- Existing db test files keep passing unchanged (no assertion edits).

Expected < 50 non-test lines plus generated migration/snapshot. No `apps/api` changes (signup bootstrap relies on the default). If an existing test outside `allowed_paths` breaks because of the new column → question, not an edit.
