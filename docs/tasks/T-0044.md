# T-0044 · Invitation preview and invite-bound signup

> Drafted by an agent at the human's request on 2026-10-24; the follow-up of T-0015-06 (`#rule-invite-signup-followup`), number assigned by Zo 2026-10-24. T-0044-01 and T-0044-02 are **answered (A)** in chat on 2026-10-24 and written as foundation §19 in PR #66. **Do not start implementation until a human has merged PR #66 (§19) and this card.** A dev agent must not edit this card.

## Goal

A person invited by email who has no account opens the invitation link, sees which shop and role it is for, sets a name and password, and becomes a staff member of that shop without creating a shop; a person who already has an account sees the same preview and logs in to accept.

## Contract (summary of §19 — the spec text wins)

- **`invitation.preview`** — `POST /invitations/preview`, public, strict `{ token }` (1–200):
  - malformed token, unknown, used, revoked, expired → `INVITATION_INVALID`; shop suspended → `ORG_SUSPENDED`; body → `VALIDATION_FAILED`;
  - 200 `{ orgDisplayName, role, branchNames, email, expiresAt }` (`branchNames` of that invitation, sorted by name; `[]` for org-wide roles); no account-existence field; no writes, no locks, no audit.
- **`auth.signupWithInvitation`** — `POST /auth/signup/invitation`, public, strict `{ token, displayName, password }`:
  - abuse limit 5 / hour / trusted IP, key prefix `signup-invite`, counted before the transaction (Valkey outage → `INTERNAL`, fail closed, as signup);
  - one transaction: invitation checks as `invitation.accept` steps 6–10 (locks included) **without** the user-email comparison (the new account takes the invitation's email) → `INVITATION_INVALID` / `ORG_SUSPENDED` / `INTERNAL` (no subscription); existing user with that email → `CONFLICT`; create user (`emailVerified = true`, not managed, name = `displayName`) via the identity public service; accept write via the org public service (membership + branches, `accepted_at`, audit `staff.joined`, actor = new user);
  - 201 `{ orgId, role }`; no session, no cookie, no email sent.

Out of scope: web screens (T-0047), changing `auth.signup` or `invitation.accept` behaviour, auto-login, resending invitations.

## Deliverables

- Contracts: `invitation.preview` request/response (`packages/contracts/src/org/`), `auth.signupWithInvitation` request/response (`packages/contracts/src/identity/`).
- Org module: preview use case + route; a public function that performs the accept write for a given user inside the caller's transaction (refactor of the T-0042 use case — behaviour of `invitation.accept` unchanged).
- Identity module: signup-with-invitation use case + route; rate-limit key prefix; user creation through the existing identity internals.

## Tests (write first)

Integration tests on real Postgres + Valkey.

- **preview:** happy path (exact body; branch names only of the invitation; email as invited); malformed / unknown / used / revoked / expired → `INVITATION_INVALID`; suspended → `ORG_SUSPENDED`; body errors; no row written (audit and invitation unchanged); token never in logs.
- **signup with invitation:** happy path — user created verified and not managed, membership active with role/branches, invitation `accepted_at`, one `staff.joined` audit row (actor = new user), 201 body, no `set-cookie`, no email sent; the new user can log in (and is not asked to verify); each invitation error; existing email (any case) → `CONFLICT` and nothing written; password length (F11); `displayName` length; 6th attempt in an hour → `RATE_LIMITED`; Valkey down → `INTERNAL` with nothing written; forced audit failure → `INTERNAL`, rollback (no user, no membership, invitation unused); race with `staff.invitation.revoke` and with a second signup on the same token → exactly one winner (T-0042 forced-order technique).
- **regression:** `invitation.accept` and `auth.signup` suites unchanged and green.
- No `FORBIDDEN`/other-org cases: both endpoints are public; tenant isolation is proven by the token's org (a token for org A never writes in org B).
