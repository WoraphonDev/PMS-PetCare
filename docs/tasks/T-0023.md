# T-0023 · Signup, verify-email and login screens

>
> **Release gate** (`#accept-signup-verification`): signup must not be opened to real users until this card is merged and deployed, because the API already requires verified email to log in.

## Goal

A new shop owner can sign up, open the verification link from the email, verify, and log in; a user whose email is not verified (or whose link broke) can ask for a new link. The screens never claim the email was delivered.

## Design

### Shared pieces this card creates (later cards reuse them)

- `src/lib/form-errors.ts`: turns `ApiError` `VALIDATION_FAILED` `details.fields` into per-field messages; unknown fields fall back to a form-level message. Forms use plain React state and the contract schema's `safeParse` for client-side checks — **no form library**.
- `src/i18n/th/errors.ts`: one generic Thai message per `ErrorCode` (copy below); screens override where the spec needs a specific text.
- `packages/api-client/src/endpoints/identity.ts`: add `auth.signup`, `auth.email.verify`, `auth.email.verification.resend`, `auth.login` descriptors (one entry per line, alphabetical).

### `scr-auth-signup` — `/signup`

- Fields (labels from §7): ชื่อ, อีเมล, รหัสผ่าน, ชื่อร้าน, slug, ชื่อสาขาแรก.
- **slug auto-fill:** while the user has not edited the slug field, it is derived from ชื่อร้าน: lowercase; ASCII letters/digits kept; spaces and `-` become one `-`; other characters dropped; trimmed of `-`; cut to 40. If that gives fewer than 3 characters (e.g. a Thai-only name), the field stays empty and shows the hint. Once the user edits the slug, auto-fill stops. Client check = contract regex `^[a-z0-9-]{3,40}$`.
- Submit → 201 → replace the form with the "check your email" panel (copy `sent`), which **does not** say the email was delivered, plus a link to `/verify-email` for resend. No auto-login.
- Errors: `VALIDATION_FAILED` → field messages; `CONFLICT` → form message `conflict` (email or slug already used — the API does not say which); `RATE_LIMITED`, `INTERNAL` → `errors.ts`.

### `scr-auth-verify-email` — `/verify-email`

- On mount, read `location.hash`; if it has `token=`, **first** remove it with `history.replaceState(null, "", "/verify-email")`, **then** `POST /auth/email/verify` with `{ token }` as JSON. The token is never put in a query string, never logged, and never sent anywhere else (the app has no analytics; nothing may be added).
- States:
  - `pending` — while posting;
  - `success` — 204: message + button to `/login` (no auto-login);
  - `invalid` — `VALIDATION_FAILED` with `details.fields.token`: one message for invalid/expired/reused/replaced (the API does not distinguish them; the UI must not guess which) + resend form;
  - `network` — `ApiError` status 0 or `INTERNAL`: retry button (re-posts the same token held in memory only) + resend form;
  - `noToken` — opened without a fragment (e.g. from the login page): resend form only.
- Resend form: one email field → `POST /auth/email/verification/resend` → always the same acknowledgement `resendAck` for any 204, which does not say whether an account exists or an email was sent; `VALIDATION_FAILED` → field message; `INTERNAL` → `errors.ts`.

### `scr-auth-login` — `/login`

- Fields: "อีเมลหรือชื่อผู้ใช้", รหัสผ่าน; link "ลืมรหัสผ่าน" → `/forgot-password` (route built by T-0045); link `notVerified` → `/verify-email`.
- Submit → 200:
  - `twoFactorRequired: true` → navigate to `/login/2fa` (T-0045);
  - else `mustChangePassword: true` → navigate to `/change-password` (T-0045);
  - else → navigate to `/` (T-0024 decides where the user lands).
- Error handling is local: `auth.login` never uses the T-0024 session-expiry redirect (it is a credential call). `UNAUTHENTICATED` → one message `failed` for wrong credentials **and** unverified email (the API does not distinguish; the message points to the verify link). `RATE_LIMITED` → `rateLimited`.

## Tests (write first)

Vitest + Testing Library; the api-client with a stubbed `fetch`.

- **api-client:** each new descriptor → method, path, body schema, response schema (204 → `undefined`).
- **form-errors:** field mapping, unknown field → form message, non-validation error → `errors.ts` text.
- **signup:** slug auto-fill (ASCII name, Thai-only name → empty + hint, user edit stops auto-fill, 40-char cut); client validation blocks bad slug/password (10–128); 201 → `sent` panel, no navigation to the app; `CONFLICT`, `VALIDATION_FAILED` (server field), `RATE_LIMITED` messages.
- **verify-email:**
  - with `#token=abc`: `history.replaceState` is called **before** `fetch`, the request body is `{"token":"abc"}`, the URL afterwards has no hash and no query; the token appears in no `console` call;
  - 204 → `success` with a link to `/login`; `VALIDATION_FAILED` (`fields.token`) → `invalid` + resend form; status 0 → `network`, retry re-posts the same token; `INTERNAL` → `network` state;
  - no fragment → `noToken` (resend form only), no verify request;
  - resend: 204 → `resendAck` regardless of email; `VALIDATION_FAILED` → field message.
- **login:** request body `{ identifier, password }`; routing for `twoFactorRequired` / `mustChangePassword` / plain success; `UNAUTHENTICATED` → `failed` (contains the verify hint); `RATE_LIMITED` → `rateLimited`.
- **i18n:** all keys used exist (type-checked by the T-0022 helper).
