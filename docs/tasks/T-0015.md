> Drafted by an agent at the human's request. The decisions T-0015-01 … 07 were approved by a human on 2026-10-22 and are written in `docs/spec/features/foundation.md` §14. **Do not start implementation until a human has merged this card together with §14.** A dev agent must not edit this card. `invitation.accept` is card T-0042, which depends on this one.

## Goal

Owners and managers see the shop's staff and pending invitations, invite a person by email with a role and branches (re-inviting replaces a pending invitation), and revoke a pending invitation. front_desk reads a branch-scoped staff list. F02, F03, F05 (`max_staff`) and F07 are enforced, and every seat-changing write follows the two-phase check-and-lock protocol. This PR also builds the shared pieces that T-0042 reuses.

## Contract (summary of §14 — the spec text wins)

- **Protocol** (`#rule-staff-check-and-lock`):
  - phase 1: guards, request validation and request-only rules; no lock, no write.
  - phase 2: one tenant transaction that locks the subscription row, then the invitation rows (id order), then membership rows, and re-checks state before writing. The first failing check answers, and any failure rolls back everything (no write, audit or email).
- **Capacity** (`#rule-staff-capacity`): active memberships (owner included) + unexpired pending invitations, counted in **one** SQL statement under the subscription lock. A re-invite does not count its own old row. Missing subscription → `INTERNAL`.
- **`GET /staff`** (`#contract-staff-list`): `{ members, invitations }`, the order given in §14. owner/manager see everything. front_desk is branch-scoped:
  - members of a branch role with overlapping branches, plus every active owner/manager;
  - `branchIds` intersected with the caller's branches;
  - only overlapping branch-role invitations, never owner/manager invitations.
  The managed email is `null`. groomer/caretaker → `FORBIDDEN`.
- **`POST /staff/invitations`** (`#contract-staff-invite`): error precedence as numbered in §14 (guards → body → manager role → `BRANCH_REQUIRED` → locks → branch `NOT_FOUND` → manager vs. a pending owner/manager invitation → `ALREADY_MEMBER` → `PLAN_LIMIT_REACHED`). Writes:
  - revoke old pending rows for the email;
  - insert the new row (`expires_at = now + 7 days`);
  - audit `staff.invited`.
  Then 201 `Invitation` (no token/hash), and the email after commit.
- **`DELETE /staff/invitations/{invitationId}`** (`#contract-staff-invitation-revoke`): 204; not pending / absent / other org → `NOT_FOUND`, then the manager rule → `FORBIDDEN`; no audit.
- **Token and email** (`#rule-invitation-token`): token `<orgId>.<32 random bytes base64url>`, SHA-256 hex of the whole token stored; link `${APP_ORIGIN}/invite#token=<token>`; the Thai subject and body exactly as in §14; send failures are logged without token, address or link.

Out of scope: `invitation.accept` and every cross-operation race with it (T-0042), invite-bound signup (follow-up, `#rule-invite-signup-followup`), `staff.account.create` / `staff.password.reset` (T-0016), `staff.update` / `staff.remove` (T-0017), UI (T-0026), outbox events, new error codes, permissions, audit actions, columns or migrations.

## Tests (write first)

Integration tests run on real Postgres through the existing harness, with no mock repositories. Every error assertion checks status, envelope code and `details.fields` where relevant. It also checks that nothing was written: invitation rows, membership rows, audit rows, sent emails.

- **Contracts** — `packages/contracts/src/org/staff.contracts.test.ts`: each request schema with valid bodies, trimming and lower-casing of email, `@managed.invalid` rejected, strict keys reported by name, wrong types, the role enum, `branchIds` duplicates and malformed UUIDs, owner/manager with non-empty `branchIds`.
- **Identity** — `apps/api/test/identity/staff-directory.test.ts`:
  - email lookup: no user; one user; legacy mixed-case email; managed flag;
  - profile load: email is null for managed accounts and `@managed.invalid` never appears.
- **Subscription** — `apps/api/test/subscription/staff-capacity.test.ts`: `lockStaffLimit` returns `max_staff`, fails closed without a subscription, and blocks a second transaction until the first commits.
- **`apps/api/test/org/staff.list.test.ts`:**
  - owner and manager see every row and every `branchIds`, in the §14 order;
  - front_desk sees exactly the §14 subset:
    - a member on a shared branch, with `branchIds` intersected;
    - a member only on other branches is absent;
    - owners/managers are present with `branchIds: []`;
    - overlapping branch-role invitations only;
    - no owner/manager invitations.
  - groomer/caretaker → `FORBIDDEN`; managed accounts show a username and `email: null`, and `@managed.invalid` never appears;
  - accepted, revoked and expired (fixed clock) invitations and removed members are not listed;
  - another org's rows never appear; guard errors.
- **`apps/api/test/org/staff.invite.test.ts`:**
  - happy path per role:
    - one row with the hash only, `expires_at = now + 7 days` (fixed clock);
    - one `staff.invited` audit row (`before` null, `after` as §14, no token);
    - one email to the invited address with the exact §14 subject and text and a link `${APP_ORIGIN}/invite#token=<token>` whose SHA-256 equals the stored hash;
    - 201 without token or hash.
  - re-invite of an unexpired email: the old row gets `revoked_at = now` and `updated_at = now`, the new row is issued, there is one audit row (for the new one), and the two hashes differ.
  - manager re-invite over an owner/manager invitation: an owner invites X as `manager`, then a manager invites X as `front_desk` → `FORBIDDEN`. The old row is unchanged (same hash, `expires_at`, `revoked_at` null), there is no new row, no audit row and no email. The same manager request succeeds when X's pending invitation is a branch role.
  - error precedence, one test per §14 step: guard errors; `VALIDATION_FAILED` for each field (incl. malformed branch UUID); manager asking owner/manager → `FORBIDDEN`; `BRANCH_REQUIRED`; `NOT_FOUND` for a well-formed unknown branch id **and** for another org's branch id (same response); `ALREADY_MEMBER` for an active member (a removed member and an unknown email can be invited); `PLAN_LIMIT_REACHED` (owner counted, pending counted, expired not counted, a re-invite at the limit not blocked by its own old row); `ORG_SUSPENDED`; front_desk/groomer/caretaker → `FORBIDDEN`. Also a combined body where two rules fail, to show which one answers.
  - concurrency:
    - parallel invites of different emails at `max_staff − 1` → exactly one 201;
    - parallel re-invites of the same email → afterwards exactly one pending invitation for it.
  - atomicity: a forced audit failure → `INTERNAL`, no invitation row, no email.
  - missing subscription (deleted through the platform connection) → `INTERNAL`, nothing written.
  - email failure after commit: the invitation stays, the response is unchanged, and the log line has no token, address or link.
  - captured logs (pino stream + `Logger.prototype` + `console`, as in T-0014) never contain the token.
- **`apps/api/test/org/staff.invitation.revoke.test.ts`:**
  - 204, `revoked_at = now`, no audit row; the row then no longer counts as a seat and is not listed;
  - error precedence per §14: guard errors (incl. `ORG_SUSPENDED`), malformed id → `VALIDATION_FAILED`, absent / other org / accepted / revoked / expired → `NOT_FOUND`, manager revoking an owner/manager invitation → `FORBIDDEN` (row unchanged), and `NOT_FOUND` wins over the manager rule for an already revoked owner invitation;
  - body/query rules of `#contract-branch-schedule-common` for DELETE.
