## Goal

Owners and managers can see the shop's staff and pending invitations, invite a person by email with a role and branches, and revoke a pending invitation. The invited person, logged in with the matching verified email, accepts the invitation and becomes an active member. F02, F03 and F05 (`max_staff`) are enforced, and §6 audit rows are written in the same transaction.

## Contract (spec-fixed vs pending)

Fixed by the spec today:

- `GET /staff` (`staff.read`): memberships + pending invitations.
- `POST /staff/invitations` (`staff.invite`): `{ email, role, branchIds }`; F02 (branch roles need ≥ 1 branch → `BRANCH_REQUIRED`), F03, F05; sends an email; audit `staff.invited`.
- `DELETE /staff/invitations/{invitationId}` (`staff.invite`).
- `POST /invitations/accept` (user): `{ token }`; F03; audit `staff.joined`.
- F03: single use, expires 7 days after creation, the accepting user's email must equal the invitation email (`INVITATION_INVALID`), already a member → `ALREADY_MEMBER`, re-inviting an email that has an unexpired invitation revokes the old one and issues a new one.
- ¹: a manager cannot act on owners/managers and cannot make anyone an owner/manager → `FORBIDDEN`.
- F05: inviting beyond `max_staff` → `PLAN_LIMIT_REACHED`; pending invitations count.
- F04 `ORG_SUSPENDED` on every write; F07 other-org ids → `NOT_FOUND`; `token_hash` stores SHA-256 only and is never returned; the token is never logged.

Pending human answers (recommendation in brackets — implement only what §14 says):

- T-0015-01 `staff.list` — [200 `{ members, invitations }`; active members only; front_desk sees the whole list read-only; managed accounts show `username`, never the internal email].
- T-0015-02 `staff.invite` — [201 `Invitation` DTO without token; email trimmed + lower-cased; owner/manager must send `branchIds: []`; unknown branch id → `VALIDATION_FAILED`; inactive branch allowed].
- T-0015-03 F05 count — [active memberships (owner included) + unexpired pending invitations, under a `FOR UPDATE` lock on the subscription row; re-invite replaces, so it is not counted twice; no re-check at accept].
- T-0015-04 token + email — [token = `<orgId>.<32 random bytes base64url>`, hash = SHA-256 of the whole token, accept reads the org id and looks up under that tenant; link `${APP_ORIGIN}/invite/<token>` per `#scr-invite-accept`; email after commit in background, failure logged without token/email].
- T-0015-05 `invitation.accept` — [session user, no `X-Org-Id`; 200 `{ orgId, membershipId, role, branchIds }`; unknown/malformed/expired/used/revoked/email mismatch/managed account → `INVITATION_INVALID`; active member → `ALREADY_MEMBER` and the invitation stays usable; removed member → membership reactivated; `display_name` = `user.name`; suspended org → `ORG_SUSPENDED`].

## Tests (write first)

Integration tests on real Postgres through the existing harness; no mock repositories. Every error assertion checks status, envelope code, `details.fields` where relevant, and that nothing was written (invitation rows, membership rows, audit rows, sent emails).

- Contracts: `packages/contracts/src/org/staff.contracts.test.ts` — every request schema: valid bodies, trimming/lower-casing, strict keys reported by name, wrong types, role enum, `branchIds` duplicates/non-UUID per §14.
- `apps/api/test/org/staff.list.test.ts`: owner, manager and front_desk see the §14 shape; groomer/caretaker → `FORBIDDEN`; managed account shows username and no `@managed.invalid`; accepted/revoked/expired invitations are not listed; other org's rows never appear; guard errors.
- `apps/api/test/org/staff.invite.test.ts`:
  - happy path per role: one invitation row (hash only, `expires_at = now + 7 days` with a fixed clock), one `staff.invited` audit row with no token in `before`/`after`, one email to the invited address whose link contains the token, response without token/hash.
  - re-invite of an unexpired email: old row gets `revoked_at = now`, new row issued, only the new token works.
  - errors: `VALIDATION_FAILED` (each field), `BRANCH_REQUIRED`, other-org or unknown branch id per §14, `ALREADY_MEMBER`, `PLAN_LIMIT_REACHED` (incl. pending invitations counted, expired not counted), manager inviting owner/manager → `FORBIDDEN`, front_desk/groomer/caretaker → `FORBIDDEN`, `ORG_SUSPENDED`, guard errors.
  - concurrency: parallel invites at `max_staff − 1` → exactly one succeeds.
  - atomicity: forced audit failure → `INTERNAL`, no invitation row, no email sent.
  - email failure after commit: invitation stays, response unchanged, log line has no token or address.
- `apps/api/test/org/staff.invitation.revoke.test.ts`: 204 and `revoked_at = now`; revoked token no longer accepts; each §14 error incl. other org → `NOT_FOUND` and the manager rule.
- `apps/api/test/org/invitation.accept.test.ts`:
  - happy path: membership `active` with the invitation's role and branches, `accepted_at = now`, `staff.joined` audit (actor = accepting user), `me.get` shows the new membership; works without `X-Org-Id`.
  - `INVITATION_INVALID` for unknown, malformed, expired (fixed clock at `expires_at` and after), already accepted, revoked, replaced by a re-invite, email mismatch (incl. case-only difference counts as a match), managed account; `ALREADY_MEMBER`; removed member re-joins per §14; `ORG_SUSPENDED`; `UNAUTHENTICATED`; `PASSWORD_CHANGE_REQUIRED`.
  - parallel double accept of one token → exactly one membership.
  - the token never appears in responses, audit rows or captured logs (pino stream + `Logger.prototype` + `console`, as in T-0014).
- `apps/api/test/subscription/staff-capacity.test.ts`: `lockStaffLimit` returns `max_staff` and fails closed without a subscription.
