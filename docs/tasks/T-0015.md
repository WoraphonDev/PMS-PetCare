# T-0015 · Staff list, email invitations and invitation accept API

## Goal

Owners and managers see the shop's staff and pending invitations, invite a person by email with a role and branches, and revoke a pending invitation. A person who **already has an account and is logged in**, with the invited email, accepts the invitation and becomes an active member. Whether that email must be verified at accept time is decided in T-0015-05. F02, F03, F05 (`max_staff`) and F07 are enforced. §6 audit rows are written in the same transaction as the change.

People without an account are not covered here (T-0015-06). `auth.signup` always creates a new shop and must not be used as a workaround.

## Contract

### Fixed by the spec today

- `GET /staff` (`staff.read`): memberships and pending invitations.
- `POST /staff/invitations` (`staff.invite`): `{ email, role, branchIds }`; F02 (branch roles need at least one branch → `BRANCH_REQUIRED`), F03, F05; sends an email; audit `staff.invited`.
- `DELETE /staff/invitations/{invitationId}` (`staff.invite`).
- `POST /invitations/accept` (user): `{ token }`; F03; audit `staff.joined`.
- F03: single use; expires 7 days after creation; the accepting user's email must equal the invitation email (`INVITATION_INVALID`); already a member → `ALREADY_MEMBER`; re-inviting an email that has an unexpired invitation revokes the old one and issues a new one.
- ¹: a manager cannot act on owners or managers and cannot make anyone an owner or manager → `FORBIDDEN`.
- F05: inviting beyond `max_staff` → `PLAN_LIMIT_REACHED`; pending invitations count.
- F04: every write → `ORG_SUSPENDED`.
- F07: an id of another org → `NOT_FOUND`, never `FORBIDDEN`. This applies to body ids too. A malformed UUID → `VALIDATION_FAILED` with `details.fields.<key>`. A well-formed UUID that is not found under the current tenant → `NOT_FOUND`, whether it does not exist or belongs to another org. **No cross-tenant query** is made to tell the two apart.
- `token_hash` stores the SHA-256 only and is never returned. The token is never logged or audited.

### Shared lock protocol (proposed in T-0015-03; applies to invite, re-invite, revoke and accept, and later to T-0016 / T-0017 writers that change seats)

Each operation is **one tenant transaction** (`ctx.db.run` or `withTenant(orgId)`). All status checks happen after the locks, in that same transaction, and before any write. Locks are always taken in this order, and a step an operation does not need is skipped, never reordered:

1. the org's `subscription` row, `FOR UPDATE` (`lockStaffLimit`);
2. the `invitation` rows involved, `FOR UPDATE`, in id order: invite and re-invite lock the pending rows for that email; revoke and accept lock their one row;
3. the `membership` row for (org, user), `FOR UPDATE`, when it exists (accept, and the `ALREADY_MEMBER` check of invite).

Step 1 for accept is not a limit re-check. Accept does not compare against `max_staff` (the seat was reserved at invite time). It takes the lock only so that "pending invitation → active membership" is serialised against invite's count and re-invite's revoke. Lowering a plan does not change pending invitations (T-0015-03).

## Deliverables

- **Contracts** — `packages/contracts/src/org/staff.list.ts`, `staff.invite.ts`, `staff.invitation.revoke.ts` (+ `invitation.accept.ts` if not split): Zod requests/responses and status constants per §14, exported from `packages/contracts/src/org/index.ts` (one line each, alphabetical).
- **Subscription** — `apps/api/src/modules/subscription/staff-capacity.ts`: `lockStaffLimit(ctx: TxContext)` returning `max_staff` (null = unlimited), same pattern as `lockBranchLimit`; exported from `subscription/index.ts`.
- **Identity read API** — `apps/api/src/modules/identity/staff-directory.ts`, exported from `identity/index.ts`. Org reaches identity tables only through these functions (ADR-0002); it never reads `"user"` itself. Two read-only operations, which run **on the caller's tenant transaction** (like `findVerificationRecipient(tx, …)`) so the identity read and the tenant writes see one transaction:
  - look up user ids by canonical email (`lower(email)`). It returns only what invite needs: the ids and whether each is managed. It returns several rows if legacy mixed-case duplicates exist, and none if no user has that email.
  - load the profiles of a set of user ids for `staff.list`: name, email (null for managed accounts), username, `twoFactorEnabled`.
  Signatures are fixed by the implementer after reading the code; the card fixes only the behaviour.
- **Invite's `ALREADY_MEMBER` check:** look up user ids by email (identity), then read and lock their `membership` rows under the tenant transaction (org repository). The outcomes:
  - no user, or users with no membership → continue;
  - an `active` membership → `ALREADY_MEMBER`;
  - only a `removed` membership → continue (re-invite allowed per T-0015-02).
  Limitation to document in code: the user rows are not locked. A signup or email change committed after the lookup is not seen, and the invitation is then checked again at accept time (email match + membership lock), which is where membership is decided.
- **Org module** — `apps/api/src/modules/org/`:
  - a staff repository (memberships, membership branches, invitations, the single-statement seat count) and lock helpers in the shared order;
  - `invitation-token.ts`: generate, hash, parse per T-0015-04;
  - `invitation-email.ts`: message builder with the Thai text from §14 and the fragment link;
  - use cases `staff.list.ts`, `staff.invite.ts`, `staff.invitation.revoke.ts`;
  - routes in a new `staff.controller.ts` (org-scoped), registered in `org.module.ts`.

  - profile load: email is null for managed accounts and `@managed.invalid` never appears.
- **`apps/api/test/org/staff.list.test.ts`:**
  - owner and manager callers see the full §14 shape;
  - a front_desk caller sees exactly the T-0015-01 subset (branch overlap, owners/managers, filtered `branchIds`, invitation filter) and nothing from branches outside its scope;
  - groomer/caretaker → `FORBIDDEN`;
  - managed accounts show a username and no `@managed.invalid`;
  - accepted, revoked and expired invitations are not listed;
  - other org's rows never appear; guard errors.
- **`apps/api/test/org/staff.invite.test.ts`:**
  - happy path per role:
    - one invitation row storing the hash only, with `expires_at = now + 7 days` (fixed clock);
    - one `staff.invited` audit row with no token in `before`/`after`;
    - one email to the invited address whose link is `/invite#token=…` (fragment);
    - a response without token or hash.
  - re-invite of an unexpired email: the old row gets `revoked_at = now`, a new row is issued, and only the new token works.
  - errors:
    - `VALIDATION_FAILED` for each field, incl. a malformed branch UUID;
    - `BRANCH_REQUIRED`;
    - `NOT_FOUND` for a well-formed branch id that is unknown **and** for another org's branch id (same response, no cross-tenant lookup);
    - `ALREADY_MEMBER` (active member); a removed member can be invited;
    - `PLAN_LIMIT_REACHED`: pending invitations counted, expired not counted, a re-invite at the limit is not blocked by its own old row;
    - `FORBIDDEN`: manager inviting an owner/manager, and front_desk/groomer/caretaker callers;
    - `ORG_SUSPENDED`; guard errors.
  - concurrency: parallel invites at `max_staff − 1` → exactly one succeeds.
  - atomicity: a forced audit failure → `INTERNAL`, no invitation row, no email.
  - email failure after commit: the invitation stays, the response is unchanged, the log line has no token or address.
- **`apps/api/test/org/staff.invitation.revoke.test.ts`:**
  - 204 and `revoked_at = now`; the revoked token no longer accepts;
  - each §14 error, incl. malformed id → `VALIDATION_FAILED`, other org → `NOT_FOUND`, and the manager rule.
- **`apps/api/test/org/invitation.accept.test.ts`** (accept card if split):
  - happy path:
    - membership `active` with the invitation's role and branches, and `accepted_at = now`;
    - one `staff.joined` audit row (actor = accepting user);
    - `me.get` shows the new membership; works without `X-Org-Id`.
  - `INVITATION_INVALID` for each unusable token:
    - unknown; malformed;
    - expired (fixed clock at `expires_at` and after);
    - already accepted; revoked; replaced by a re-invite;
    - email mismatch (a case-only difference counts as a match);
    - managed account.
  - `ALREADY_MEMBER`; a removed member re-joins per §14; `ORG_SUSPENDED`; `UNAUTHENTICATED`; `PASSWORD_CHANGE_REQUIRED`.
  - **unverified email:** a session of a real-email user with `email_verified = false` (seeded directly) gets the result T-0015-05 decides, and nothing is written.
  - the token never appears in responses, audit rows or captured logs (pino stream + `Logger.prototype` + `console`, as in T-0014). This does not prove that proxies or browsers keep the token private; the fragment link (T-0015-04) is the control for that.
- **Races** (in whichever PR contains both operations; with the split, these run in the accept card):
  - **invite vs accept:** accept converts a reserved seat (pending X) into an active membership, so the count does not change, whatever the commit order. At `max_staff` (X included), a parallel invite of a new email is **always** `PLAN_LIMIT_REACHED` and the accept succeeds. At `max_staff − 1` the invite **always** succeeds. Afterwards, active memberships + pending invitations ≤ `max_staff`. Repeat each case enough times to hit both orders.
  - **re-invite vs accept** (same email): the result is either (accept wins → membership active, re-invite → `ALREADY_MEMBER`, no new invitation) or (re-invite wins → old invitation revoked, accept → `INVITATION_INVALID`, no membership, new invitation pending). Never both a new membership and a new pending invitation for that email.
  - **revoke vs accept:** either (revoke wins → 204, accept → `INVITATION_INVALID`, no membership) or (accept wins → membership active, revoke → `NOT_FOUND`). No membership is ever created from a token whose revoke committed first.
  - **double accept** of one token: exactly one 200 and one `INVITATION_INVALID`; one membership row; one `staff.joined` audit row.
- **`apps/api/test/subscription/staff-capacity.test.ts`:** `lockStaffLimit` returns `max_staff`, fails closed without a subscription, and blocks a second transaction until the first commits.
