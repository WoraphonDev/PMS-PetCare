# T-0040 · Let DELETE bodies without Content-Type reach the route

## Goal

Close the limitation recorded in T-0013-01 (answered 2026-10-22: accept as a known limitation for T-0013, fix in a separate infra card). Today Fastify 5 rejects a DELETE that carries a body but no `content-type` **before routing**. The error filter turns that into `400 VALIDATION_FAILED "Request rejected"` without `details`. So the route's own rule (`#contract-branch-schedule-common`: nonempty body → `VALIDATION_FAILED` at `_`, absent/zero-byte body accepted) never runs. After this card such a request reaches the route handler, and the existing `assertNoBody` in the org module decides.

## Read first

- `docs/questions/T-0013-01.md` (measured cases and options)
- `docs/spec/features/foundation.md#contract-branch-schedule-common`, `#errors`
- `apps/api/src/create-app.ts` (Fastify adapter, hooks), `apps/api/src/common/error.filter.ts` (read only — Fastify client-error mapping)
- `apps/api/src/modules/org/org-body.pipe.ts` `assertNoBody` (read only — the consumer of the parsed body)
- Fastify 5 `handle-request.js` / content-type parser docs: requests without `content-type` are parsed with the `''` content type

## Deliverables

- `create-app.ts`: register a content-type parser for requests **without** a `content-type` header, so they reach the route with the raw payload. Buffer it with Fastify's existing `bodyLimit`. Represent it as a string: an empty body becomes `""`, which `assertNoBody` already accepts. Keep it next to the other Fastify setup with a one-line comment citing T-0013-01.
- Requests **with** a content-type must behave exactly as today. That covers JSON, `text/plain`, an unknown media type (still `VALIDATION_FAILED` with `fields.body` via the error filter), and an empty `application/json` body.
- POST/PUT/PATCH routes keep their current responses for bodies without a content-type. The route's Zod pipe now receives a string instead of Fastify rejecting it earlier. If that changes any existing test's status, code or `details` field path, stop and write a question. Do not edit those tests.
- No change to `error.filter.ts`, guards, module code, spec or other tests outside `allowed_paths`.

## Tests (write first)

- `apps/api/test/common/body-without-content-type.test.ts` (new), real app via the existing harness, against the T-0013 route `DELETE /branches/{branchId}/closures/{closureId}`:
  - no content-type + `content-length: 1` body → 400 `VALIDATION_FAILED` with `details.fields._`, and nothing deleted
  - no content-type + empty chunked body → 204, and the closure is deleted
  - no content-type + nonempty chunked body → 400 at `_`
  - unknown content-type with a body → unchanged from today (assert the current status/code/details)
  - a no-content-type body larger than `bodyLimit` → rejected, never buffered unbounded (assert the current 413 → `VALIDATION_FAILED` mapping)
- One POST and one PUT route each get a body without content-type. Assert the response equals what main returns today: record it first (RED/GREEN evidence), then lock it in the test.
- `apps/api/test/org/support.ts` `expectNoBodyRule`: extend the DELETE case to include requests without a content-type, now that they reach the route. Adjust the closure count in `branch.closure.delete.test.ts` only for the extra accepted call, with a comment.
