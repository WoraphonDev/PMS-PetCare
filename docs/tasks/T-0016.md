# T-0016 · Managed staff accounts: create and password reset API

> Drafted by an agent at the human's request. Decisions T-0016-01 … 05 were approved by a human on 2026-10-23 and are written in `docs/spec/features/foundation.md` §15. The human set `human_review: false`. **Do not start implementation until a human has merged this card together with §15.** A dev agent must not edit this card.

## Goal

Owners and managers create a username + password account for staff without an email (F09, Q-0006). The new account must change its password at first login. They can also reset that account's password, which forces a new password change and signs the account out everywhere. Both follow F02, F05 (`max_staff`) and ¹, the §14 check-and-lock protocol, and write a §6 audit row in the same transaction.

## Contract

### Fixed by the spec today

- `POST /staff/accounts` (`staff.invite`): `{ displayName, username, password, role, branchIds }`; F02, F05, F09; `CONFLICT` for a taken username; audit `staff.account_created`.
- `PUT /staff/{membershipId}/password` (`staff.update`): `{ newPassword }`; F09; audit `staff.password_reset`.
- F09:
  - the account belongs to the creating org; it has no email recovery;
  - a password set by owner/manager → `must_change_password = true`;
  - reset only for this org's managed accounts (`MANAGED_ACCOUNT_ONLY`);
  - a reset clears every session of the account;
  - the account counts in `max_staff`.
- F11 password length 10–128 → `VALIDATION_FAILED`. Username `^[a-z0-9._-]{3,40}$`, unique platform-wide.
- ¹ manager limits (`FORBIDDEN`); F04 `ORG_SUSPENDED`; F07 other-org ids → `NOT_FOUND`.
- §14: create is a seat-changing writer (subscription lock first, then membership; re-check after the locks).
- Managed accounts store `<user_id>@managed.invalid`, never shown or mailed; `email_verified` is never set true for them.
- `#rule-email-login-policy`: managed accounts are exempt from email verification only; F09 owning membership, must-change-password and F10 2FA still apply.
- Passwords and hashes never appear in responses, audit rows or logs.

### Decided in §15 (summary — the spec text wins)

- **Roles** (`#rule-managed-account-roles`): an owner may create any role; a manager only branch roles.
- **Identity rows** (`#rule-managed-account-identity`): an identity public function on org's tenant transaction inserts `user` (placeholder `<id>@managed.invalid`, `email_verified` false, `is_managed`, `managed_by_org_id`, `must_change_password`) + credential `account` hashed with Better Auth's hasher; no session, no email.
- **Create** (`#contract-staff-account-create`): 201 `StaffMember`; username trimmed + lower-cased then the regex; `displayName` 1–100 also becomes `user.name`. Error order: guards → body → manager role → `BRANCH_REQUIRED` → subscription lock + org status → branch `NOT_FOUND` → `PLAN_LIMIT_REACHED` → `CONFLICT`. Audit `after { username, displayName, role, branchIds }`.
- **Username-only login** (`#rule-email-login-policy`, T-0016-05): an email identifier (contains `@`) that resolves to an `isManaged` user, incl. `<user_id>@managed.invalid`, is refused like a wrong password — the presented password is hashed as today, the failure counter records it, `UNAUTHENTICATED`, no session or cookie. Decided by the account's `is_managed`, not by the suffix. Username login and real-email login are unchanged.
- **Reset** (`#contract-staff-password-reset`): 204. Error order: guards → `VALIDATION_FAILED` → membership lock: absent / other org / removed → `NOT_FOUND` → org status `ORG_SUSPENDED` → manager rule `FORBIDDEN` → `MANAGED_ACCOUNT_ONLY`. No subscription lock (no seat changes). Writes: new hash, `must_change_password = true`, every session deleted, audit with `before`/`after` null; 2FA unchanged.

Out of scope: `staff.update` / `staff.remove` (T-0017), disabling a managed account (T-0017 via remove), 2FA reset by owner/manager, any login change other than the username-only rule, any change to `PasswordChangeGuard`, rate limits on these endpoints, UI (T-0026), new error codes, permissions, audit actions, columns or migrations.

## Tests (write first)

Integration tests run on real Postgres through the existing harness, with no mock repositories. Every rejection compares a full snapshot (memberships, membership branches, audit; the identity rows of the target or the would-be account) before and after.

- **Contracts:** `packages/contracts/src/org/staff.accounts.contracts.test.ts`, covering both bodies:
  - username trimming/lower-casing and the regex (too short, too long, `@`, spaces, other symbols);
  - password 9 / 10 / 128 / 129 characters, not trimmed;
  - `displayName` limits; role/branch rules; strict keys.
- **Identity** — `apps/api/test/identity/managed-account.test.ts`:
  - created rows: placeholder email = `<id>@managed.invalid`, `email_verified` false, `is_managed`, `managed_by_org_id`, `must_change_password`, a credential account whose hash verifies the password;
  - nothing is written when the caller's transaction rolls back;
  - the set-password function deletes every session.
- **Login** — `apps/api/test/identity/managed-login.test.ts` (existing login tests stay green unchanged):
  - managed account + correct password via `<user_id>@managed.invalid` → `UNAUTHENTICATED`, same envelope as a wrong password, no `Set-Cookie`, no `session` row; the failure counter increases (enough such attempts → `RATE_LIMITED`, as with wrong passwords);
  - the same with upper-case / mixed-case placeholder email;
  - the presented password is hashed on this path (spy on the hasher, as the existing policy-failure tests do);
  - the same account via its username → logs in (then `PASSWORD_CHANGE_REQUIRED` as usual);
  - regression: a real-email verified account still logs in by email and by username; an unverified real-email account is still refused.
- **`apps/api/test/org/staff.account.create.test.ts`:**
  - happy path (owner and manager callers):
    - 201 `StaffMember` (`email` null, `isManaged` true, `username`);
    - membership + branches;
    - audit `staff.account_created` with no password/hash;
    - the account appears in `GET /staff`;
    - **end to end** (existing login and `PasswordChangeGuard`, unchanged), with a managed `front_desk` account (has `staff.read`):
      - login with the username works;
      - before the change: `GET /staff` (with `X-Org-Id`) → `PASSWORD_CHANGE_REQUIRED`; the guard's existing exceptions still work — `GET /me` → 200, and `POST /auth/password/change` is accepted;
      - after `POST /auth/password/change`: `GET /staff` → 200;
      - login with the placeholder email → `UNAUTHENTICATED`, no session (`#rule-email-login-policy`);
    - no email is sent.
  - error precedence, one test per §15 step plus a combined case:
    - guards (incl. `ORG_SUSPENDED`);
    - `VALIDATION_FAILED` per field; manager asking owner/manager → `FORBIDDEN`; `BRANCH_REQUIRED`;
    - other-org/unknown branch → `NOT_FOUND`; `PLAN_LIMIT_REACHED` (owner, pending invitations and managed accounts counted);
    - `CONFLICT` for a username already used (case-insensitively) by a managed or a real-email account;
    - roles without `staff.invite` → `FORBIDDEN`.
  - role rule: a manager asking owner/manager → `FORBIDDEN`; an owner may create a managed owner and manager.
  - concurrency:
    - two parallel creates with the same username → one 201, one `CONFLICT`, one account;
    - parallel creates at `max_staff − 1` → one 201.
  - suspension while waiting on the subscription lock → `ORG_SUSPENDED` (§14 re-check), nothing written.
  - atomicity: a forced audit failure → `INTERNAL`, no user, account, membership or audit row.
  - captured logs (pino stream + `Logger.prototype` + `console`) never contain the password, its hash or the username on failure paths. A failing-query test plus a mutation check, as in T-0015.
- **`apps/api/test/org/staff.password.reset.test.ts`:**
  - happy path:
    - 204; the old password no longer logs in; the new one logs in, then gets `PASSWORD_CHANGE_REQUIRED`;
    - every existing session of the account is rejected (`UNAUTHENTICATED`), incl. one that had passed 2FA;
    - 2FA settings unchanged;
    - audit `staff.password_reset` with no password/hash.
  - error precedence per §15:
    - guards; malformed id / body;
    - absent / other-org / removed membership → `NOT_FOUND`;
    - suspended org;
    - manager → owner/manager target → `FORBIDDEN` (also when that target is not managed: no information leak);
    - real-email account → `MANAGED_ACCOUNT_ONLY`; a managed account of another org that is a member here → `MANAGED_ACCOUNT_ONLY`;
    - roles without `staff.update` → `FORBIDDEN`.
  - atomicity: a forced audit failure → `INTERNAL`, password, flag and sessions unchanged.
  - logs never contain the new password or hash.
