## Goal

A platform admin who has passed 2FA searches shops, opens one, suspends or reactivates it with a reason, and changes its plan, period end and internal note.

## Design

### Access — layout `_app.platform`

- Not `me.user.isPlatformAdmin` → `errors.FORBIDDEN` text, no platform request.
- Admin with `twoFactorEnabled = false` → `setup2fa` message + link to `/account/security` (F10: "ถ้ายังไม่เคยตั้ง 2FA ให้ไปหน้าตั้งค่าก่อน"); no platform request.
- Any platform request answering `TWO_FACTOR_REQUIRED` (session not 2FA-verified) → `verify2fa` message + link to log in again.
- Platform requests never send `X-Org-Id`.

### `/platform/orgs` — search

- Search box `q` (1–100, debounced, trimmed), status filter (ทั้งหมด / ใช้งาน / ระงับ) → `GET /platform/orgs` → rows: display name, slug, status badge, plan name, usage (สาขา n · พนักงาน n), created date. "โหลดเพิ่ม" with `nextCursor`; changing filters restarts.
- Row → `/platform/orgs/:orgId`. Listing writes no audit.

### `/platform/orgs/:orgId` — detail

- **Every `GET /platform/orgs/{orgId}` writes an audit row `platform.org_viewed` that the shop owner sees.** So the detail query must fetch **once per visit**: `staleTime: Infinity`, no refetch on window focus, reconnect or mount of child components; after a status or plan change, put the **200 response** (same detail shape) into the cache — never refetch.
- Sections: shop (`organization` fields, status), owners (name, email or username), plan (name, code, limits, `formatBaht` price, started, period end, note), usage (branches, staff active + pending = total).
- **Suspend / reactivate:** button opposite to the current status → dialog with required reason (1–500) and a warning text → `PUT /platform/orgs/{id}/status` `{ status, reason }` → 200 → cache = response.
- **Change plan:** dialog prefilled with the current values (PUT replaces: omitted `currentPeriodEnd`/`note` = null, so the form always sends all three):
  - plan select from `GET /platform/plans` — inactive plans shown disabled with `inactivePlan`; each option shows name, limits and price;
  - period end: a Bangkok date or "ไม่มีวันหมดอายุ" (`null`). The API stores an instant; the UI sends `bangkokDayStartUtc(chosenDate + 1 day)` — the start of the day **after** the chosen date — so "ใช้ได้ถึงวันที่ X" includes all of day X. When showing an existing value, display the Bangkok date of (instant − 1 ms) so a value saved here round-trips to the same date. (UI convention approved by merging this card; MVP enforces no expiry anyway.)
  - note (≤ 500, internal — `noteHint`: not shown to the shop and not audited);
  - if the chosen plan's limit is below current usage, show `downgradeWarning` (allowed; existing data stays, new additions blocked);
  - → `PUT /platform/orgs/{id}/subscription` → 200 → cache = response. `VALIDATION_FAILED` at `planCode` (plan became inactive) → message + reload plans.
- `NOT_FOUND` → not-found state; malformed id → not-found state without a request.
- api-client: `platform.org.list`, `platform.org.get`, `platform.org.setStatus`, `platform.org.setPlan`, `platform.plan.list` in new `endpoints/platform.ts`.

## Tests (write first)

- api-client descriptors (no `X-Org-Id`).
- access: non-admin → forbidden, no request; admin without 2FA → `setup2fa`, no request; `TWO_FACTOR_REQUIRED` response → `verify2fa`.
- search: query keys, debounce, status filter, load more, restart on filter change.
- **detail fetched exactly once** per visit: window focus / re-render / opening and closing dialogs cause no second `GET`; after status and plan changes the cache equals the PUT response and no `GET` follows.
- status: reason required; body; 200 updates the badge.
- plan: form prefilled; body always has `planCode`, `currentPeriodEnd` (or null), `note` (or null); period end = start of the next Bangkok day (e.g. chosen 2026-12-31 → `2026-12-31T17:00:00.000Z`); inactive plans disabled; downgrade warning when a limit < usage; `VALIDATION_FAILED` at `planCode` → message + plans refetched.
