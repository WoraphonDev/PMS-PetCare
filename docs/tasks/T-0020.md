# T-0020 · Platform admin: change a shop's plan

> Drafted by an agent at the human's request. Decisions T-0020-01 (A) and T-0020-02 (A) were approved by a human on 2026-10-23 and are written in `docs/spec/features/foundation.md` §18. **Do not start implementation until a human has merged this card together with §18, and T-0019 is merged.** A dev agent must not edit this card. **`human_review: true`** comes from the spec: `#ep-platform.org.set_plan` is marked human_review, because a plan sets what a shop pays and its limits.

## Goal

A platform admin who has passed 2FA changes a shop's plan, its period end and the internal note (US-F08). The write locks the same subscription row as every branch/staff writer, so limits never race a plan change. Plan and period changes are audited. The admin can also list the plans to choose from (`GET /platform/plans`).

## Contract

### Fixed by the spec today

- `PUT /platform/orgs/{orgId}/subscription` `{ planCode, currentPeriodEnd?, note? }`; platform admin with 2FA; audit `platform.plan_changed`; human review.
- The subscription row is locked like branch create (#rule-branch-capacity). Inactive plans and past period ends are still enforced (no lifecycle in MVP). Money is integer satang.

### Decided in §18 (summary — the spec text wins)

- **setPlan** (`#contract-platform-set-plan`):
  - PUT replaces: `planCode` must name an active plan (else `VALIDATION_FAILED`); omitted `currentPeriodEnd`/`note` = null;
  - lock the subscription row; no-op → 200 with nothing written; `started_at = now` only when the plan changes;
  - downgrade below usage allowed (nothing removed, new additions blocked by F05);
  - audit `platform.plan_changed` (target shop's `org_id`) only for `planCode`/`currentPeriodEnd` changes; `note` never audited; 200 = platform detail.
- **Plans list** (`#contract-platform-plan-list`): `GET /platform/plans` → `{ items: [{ code, name, maxBranches, maxStaff, priceSatangPerMonth, isActive }] }` ordered by `code`.

Out of scope: billing, invoices, plan creation/editing, automatic expiry (no lifecycle in MVP), notifying shops, UI.

## Tests (write first)

Integration tests run on real Postgres.

- **Contracts:** body schema (missing `planCode`, length, instants, null/omitted handling, strict keys).
- **`apps/api/test/platform/platform.set-plan.test.ts`:**
  - change plan:
    - `plan_id`, `started_at = now`, period, note;
    - one `platform.plan_changed` audit row with changed `planCode`/`currentPeriodEnd` only and never the note;
    - `GET /subscription` of the shop shows the new plan.
  - period-only change (audit, `started_at` unchanged); note-only change (no audit row); no-op (nothing written).
  - downgrade below usage: existing branches and members stay; the next `POST /branches` and `POST /staff/invitations` → `PLAN_LIMIT_REACHED`; pending invitations still accept.
  - unknown and inactive `planCode` → `VALIDATION_FAILED`; unknown shop → `NOT_FOUND`; malformed id → `VALIDATION_FAILED`.
  - **locking:** a setPlan waiting behind a held subscription lock commits after it, and a branch create racing a downgrade sees exactly one of the two plans (never exceeds the plan it locked under). Commit order is forced the T-0042 way: hold the lock, queue both, release.
  - forced audit failure → `INTERNAL`, subscription unchanged.
  - access: `UNAUTHENTICATED`, `FORBIDDEN` (shop owner), `TWO_FACTOR_REQUIRED`.
  - plans list: order, inactive marked, admin-only.
