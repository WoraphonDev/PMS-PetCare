# T-0029 · End-to-end test of the foundation flow

> Drafted by an agent at the human's request on 2026-10-24. **Do not start implementation until a human has answered T-0029-01 and merged this card, and every card in `depends_on` is merged.** A dev agent must not edit this card.

> `#accept-signup-verification`: "T-0029 เพิ่ม signup → verify → login → invite flow". Together with T-0023 this is the gate before signup is opened to real users.

## Goal

One automated browser test proves the whole foundation works together on real services: a new owner signs up, verifies the email from the real email sent, logs in, invites a staff member, the staff member creates an account from the invitation and logs in, and the owner edits a branch.

## Design

- New private workspace package `apps/e2e` (`@app/e2e`) with `playwright.config.ts`, `global-setup.ts`, `tests/foundation.spec.ts`, helpers. **Its `test` script is not run by `pnpm verify`**: the package defines `typecheck` (joins `pnpm verify`) and `e2e` (runs Playwright); no `test` script, so Turbo's `test` task skips it.
- **Global setup** (Testcontainers, nothing on fixed ports):
  1. Postgres via `createTestDb()` (container, the three roles, all migrations). It does **not** seed plans and exposes only `runtimeUrl`, so the setup then runs `withPlatform(platformDb, seedPlans)` from `@app/db` (signup needs `mvp_free`) and derives the platform URL from `runtimeUrl` with the platform role's test credentials (`app_platform` / `platform`, as in `test-db.ts`). Do not edit `packages/db/test/**` (outside this card);
  2. Valkey and Mailpit (`axllent/mailpit:v1.31`, same image as compose) containers;
  3. build the API (`pnpm --filter @app/api build`) and start `node apps/api/dist/main.js` with env pointing at the containers (`DATABASE_URL` = runtime role, `DATABASE_PLATFORM_URL` = platform role, `VALKEY_URL`, `SMTP_URL` = Mailpit, `APP_ORIGIN` = the web origin, a random `BETTER_AUTH_SECRET`), wait for `GET /api/v1/health`;
  4. build the web and serve it with `vite preview` on a free port with `/api` proxied to the API (add `preview.proxy` to `vite.config.ts`, mirroring the dev proxy, if T-0022 did not); service worker enabled — the test runs with the real PWA build;
  5. teardown stops everything even after a failure.
- **Email:** read messages through Mailpit's HTTP API (`/api/v1/messages`, `/api/v1/message/{id}`); extract the verification link (`/verify-email#token=…`) and the invitation link (`/invite#token=…`) from the body; never print tokens in test output (mask in error messages).
- **The flow** (one spec, Chromium, viewport 390 × 844 — a phone, since §7 requires mobile use):
  1. `/signup` → fill the form (unique email/slug per run) → `sent` panel shown, no auto-login;
  2. open the verification link from Mailpit → `success`; the address bar ends with `/verify-email` (no token);
  3. `/login` as owner → shell shows the shop name and owner nav;
  4. `/settings/staff` → invite `staff+<run>@example.test` as `front_desk` on the first branch → invitation listed;
  5. new browser context (no cookies) opens the invitation link → preview shows shop + role → "ยังไม่มีบัญชี — สมัคร" → name + password → `signedUp`;
  6. staff logs in → shell shows the shop, front-desk nav (พนักงาน visible, ตั้งค่าร้าน hidden); `/settings/staff` shows themselves and the owner, no invite buttons;
  7. back as owner: `/settings/staff` lists the staff member as active, invitation gone; `/settings/branches/<first>` → change the address → saved, reload shows the new value;
  8. owner `/settings/audit` lists `staff.invited`, `staff.joined`, `branch.updated`.
- Assertions use roles/labels from the i18n copy (import the message objects, do not hard-code Thai strings twice).
- Trace + video on failure, kept as Playwright artifacts (not committed).

Out of scope: CI wiring (per T-0029-01), platform admin flow, 2FA flow, managed accounts, visual regression, other browsers.
