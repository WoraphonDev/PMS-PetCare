**บทเรียนที่นำมาออกแบบ**

1. **LINE-first:** ร้านในไทยใช้ LINE OA เป็นช่องทางหลัก และมักแยก OA ต่อสาขา ([ตัวอย่าง Pet Relax](https://www.yellowpages.co.th/lp/petrelax/catalog/item/โรงแรมสุนัข-ใกล้ฉัน-Ece4hfp)) พนักงานหน้าร้านทำงานผ่าน Line@ อยู่แล้ว ([ประกาศงาน](https://www.jobthai.com/en/job/1726259)) ระบบจึงต้องรองรับหลาย OA ต่อ 1 tenant และมี inbox รวม
2. **Pricing engine ตามน้ำหนัก / สายพันธุ์ / ขน / นิสัย** คือสิ่งที่ POS ทั่วไปทำไม่ได้ ([Qashier](https://qashier.com/th/resources-center/1238/pos-for-pet-shop))
3. **Ticket เดียวรวมทุกบริการ** (ห้องพัก + สปา + สินค้า + รับ-ส่ง, หลายตัวใน booking เดียว) และแยกรายได้ VAT / Non-VAT ตาม[คำแนะนำด้านภาษี](https://aplusme.org/blog/pet-spa-boarding-service-revenue-tax.html)
4. **Report card + รูป/วิดีโอระหว่างวัน** คือฟีเจอร์ที่ลูกค้าชอบที่สุดในรีวิว MoeGo และเป็นหัวใจของ Gingr — ส่งผ่าน LINE ได้ทันทีจะเหนือกว่า SMS/Email
5. **กฎวัคซีนบังคับใน booking engine** ไม่พึ่งดุลยพินิจพนักงาน และมีตาราง normalize ชื่อวัคซีน ([RaftLabs](https://www.raftlabs.com/blog/how-to-build-dog-daycare-management-software)) + PreCheck ก่อนวันเข้าพัก
6. **Capacity สองแบบแยกกัน:** daycare นับต่อช่วงเวลา/โซน, boarding นับต่อห้องต่อคืน และมี temperament evaluation กำหนด playgroup ([PocketSuite](https://pocketsuite.io/post/pet-daycare-software-comparison-2026/))
7. **Payment sync สองทาง + นโยบายคืนเงิน:** PromptPay ผ่าน Opn/Omise void หรือ refund ผ่าน gateway ไม่ได้ ([Omise docs](https://docs.omise.co/promptpay)) ระบบต้องคืนเป็น wallet credit หรือบันทึกการโอนคืนด้วยมือพร้อมหลักฐาน
8. **Membership / Package คือเครื่องเพิ่มรายได้ที่คู่แข่งยังทำไม่เสร็จ:** MoeGo อ้างว่า retention 12 เดือนเพิ่มจาก 66% เป็น 81% (ตัวเลขจาก vendor, [MoeGo](https://www.moego.pet/membership-loyalty)) แต่ฟีเจอร์ยัง beta
9. **AI เป็นเส้นแบ่งรุ่นใหม่:** MoeGo มี AI receptionist, Gingr ยังไม่มี ([Gingr vs MoeGo](https://www.gingrapp.com/gingr-versus-moego)) ในไทยลูกค้าทัก LINE มากกว่าโทร จุดที่คุ้มที่สุดคือ AI ตอบแชท + จองคิวใน LINE
10. **Marketplace ส่วนใหญ่ไม่มี API เปิด:** ต้องออกแบบให้รับ booking จากทุก channel (รวมการคีย์มือและ voucher) เข้า inventory เดียว และเปิด Partner API ของเราเอง
11. **โมเดลราคาไทย:** ช่วงราคาตลาดไทยอยู่ที่ 0–990 บาทต่อเดือน ต่ำกว่าต่างประเทศหลายเท่า ควรมี tier เริ่มต้นราคาใกล้เคียงและขาย CRM / Campaign / API เป็น add-on

## ชุดที่ 1 — Core Platform & Master Data

**4.2 Workflow หน้างาน**

สถานะงาน grooming เดินตามลำดับนี้ ทุกขั้นบันทึกเวลาและผู้ทำ และส่ง LINE ให้ลูกค้าตามที่ร้านตั้ง

1. **Booked** — ยืนยันแล้ว, เตือนก่อนนัด 24 ชม. และ 2 ชม. ให้กดยืนยัน / เลื่อนเองใน LINE
2. **Checked-in** — ชั่งน้ำหนัก (อัปเดตราคาอัตโนมัติถ้าข้ามช่วง), ถ่ายรูปก่อนทำ, ตรวจสภาพผิว / เห็บหมัด / บาดแผล (ติ๊กบนภาพตัวสัตว์), ยืนยันทรงตัดกับเจ้าของ (ดูรูปครั้งก่อนได้), เซ็น waiver ถ้าเป็นสัตว์ดุ / สูงอายุ
3. **Waiting** — อยู่ในกรงพักรอ, แสดงเวลารอบนบอร์ด
4. **Bathing → Drying → Grooming** — ช่างกดเริ่ม/จบทีละขั้นบนแท็บเล็ต, เพิ่ม add-on หน้างานได้เมื่อลูกค้ากดอนุมัติใน LINE, บันทึกเหตุการณ์ (บาดเล็กน้อย, ความเครียด) พร้อมรูป
5. **Ready for pickup** — ถ่ายรูปหลังทำ, ส่ง Report Card และแจ้งมารับ, เริ่มนับเวลาค่าฝากเกินเวลา (ถ้าตั้งไว้)
6. **Checked-out / Paid** — รับชำระ, ตัดแพ็กเกจ / แต้ม, คำนวณคอมมิชชั่น, เสนอจองครั้งถัดไป, 1 วันถัดไปส่งขอรีวิว
7. **Cancelled / No-show** — บันทึกเหตุผล, จัดการมัดจำตามนโยบาย, เปิด slot ให้ waitlist

## ชุดที่ 8 — CRM

| Feature | รายละเอียด | Priority |
| --- | --- | --- |
| Customer 360 | หน้าเดียว: สัตว์ทุกตัว, การจองทั้งหมด, ยอดใช้จ่ายสะสม (LTV), แต้ม, แพ็กเกจ, ยอดค้าง, แชทล่าสุด, เรื่องร้องเรียน, คะแนนความพึงพอใจ, tag, หมายเหตุภายใน | MVP |
| Unified Inbox | แชท LINE OA ทุกสาขา + Facebook Messenger + IG DM (P2) ใน inbox เดียว, มอบหมายผู้ดูแล, quick reply, ส่งลิงก์จอง/ชำระจากแชท, เห็น Customer 360 ข้างแชท | MVP (LINE) |
| Lead management | คนที่ทักถามแต่ยังไม่จอง (จากแชท, สายที่ไม่ได้รับ, ฟอร์มเว็บ, โฆษณา) → pipeline จนถึงจองครั้งแรก, เตือน follow-up | P2 |
| Segmentation | กรองด้วย: ชนิด/พันธุ์/ขนาด/อายุสัตว์, บริการที่ใช้, สาขา, RFM (มาล่าสุด / ความถี่ / ยอดเงิน), tier, ไม่มาเกิน X วัน, วัคซีนใกล้หมด, วันเกิดน้องเดือนนี้, consent การตลาด = ใช่ — segment แบบ dynamic อัปเดตเอง | MVP (พื้นฐาน) / P2 (RFM) |

| Automation journeys | Trigger → เงื่อนไข → รอ → ส่งข้อความ/คูปอง: welcome ลูกค้าใหม่, หลังใช้บริการครั้งแรก, ถึงรอบตัดขน, วันเกิดน้อง, win-back, วัคซีนหมด, หลังเกิด incident (โทรตามอาการ) | P2 |
| Task & Follow-up | งานให้พนักงานโทรตาม (ลูกค้าให้คะแนนต่ำ, ลูกค้า VIP หายไป, abandoned booking) พร้อมบันทึกผลการติดต่อ | P2 |
| Feedback & NPS | แบบสอบถามหลังใช้บริการ, NPS รายสาขา/รายช่าง, ติดตามการแก้ปัญหา (case) | MVP (ดาว) / P2 (NPS, case) |

## ชุดที่ 9 — Campaign & Promotion

Campaign = การส่งข้อความถึง segment ส่วน Promotion = กฎส่วนลดที่ POS และหน้าจองคำนวณให้เอง สองส่วนนี้แยกกันแต่ผูกกันได้ (campaign แจกคูปองของ promotion) และทุก campaign ต้องวัดผลเป็นยอดจองจริงได้

**9.1 Campaign**

| Feature | รายละเอียด | Priority |
| --- | --- | --- |
| Broadcast | ส่ง LINE (Flex / รูป / คูปอง) / SMS / Email ถึง segment, ตั้งเวลาส่ง, ประมาณจำนวนข้อความก่อนส่ง (คุมโควตา LINE OA) | MVP |
| Template library | template ไทยสำเร็จรูป: สงกรานต์ฝากน้อง, วันเกิดน้อง, หน้าฝน (เห็บหมัด), หน้าร้อน (ตัดขนสั้น), คิดถึงน้อง (win-back) | MVP |
| Personalization | ใส่ชื่อลูกค้า + ชื่อน้อง + รูปน้องล่าสุด + บริการที่ใช้บ่อย ในข้อความ | MVP |
| Scheduled & Triggered | ส่งตามเวลา หรือตาม event (ใช้ journey engine ของชุดที่ 8) | P2 |

| Attribution | นับการจอง/ยอดขายที่เกิดภายใน X วันหลังได้รับ campaign, เทียบกับต้นทุนข้อความ + ส่วนลด (ROI) | MVP |
| Ads audience | export segment เป็น custom audience ไป LINE Ads / Meta Ads (hash เบอร์, เฉพาะคนที่ยินยอม) | P3 |

**กฎการคำนวณ (ต้องตัดสินใจก่อน implement)**

1. ลำดับคำนวณตั้งต้น: ราคาฐาน (pricing engine) → สิทธิ์ membership → promotion อัตโนมัติ → คูปอง → แลกแต้มเป็นส่วนลด → ใช้แพ็กเกจ/wallet → VAT
2. แต่ละ promotion ตั้งได้ว่า “ใช้ร่วมกับโปรอื่นได้ / ไม่ได้” (stackable) และ priority — ถ้าชนกันระบบเลือกอันที่ลูกค้าได้ประโยชน์สูงสุด
3. กำหนดเพดานส่วนลดรวมต่อบิล (เช่น ไม่เกิน 40%) กันขาดทุน
4. บิลเก็บ snapshot กฎที่ใช้จริง (promotion id + version) เพื่อตรวจสอบย้อนหลัง แม้ภายหลังจะแก้โปร
5. หน้าจองออนไลน์และ POS เรียก pricing service ตัวเดียวกัน ราคาที่ลูกค้าเห็นตอนจองต้องตรงกับที่เคาน์เตอร์ (ยกเว้นน้ำหนักจริงต่างจากที่แจ้ง)

## ชุดที่ 10 — Loyalty: สะสมแต้ม, Tier, Package, Membership, Wallet

แยกเครื่องมือ 5 ตัวที่ต่างกันทางบัญชีออกจากกันตั้งแต่ data model — แต้มเป็นสิทธิประโยชน์, แพ็กเกจและ wallet เป็นหนี้ที่ร้านต้องให้บริการ (deferred revenue), membership เป็นรายได้ประจำ ทุกตัวใช้ ledger แบบ append-only

| เครื่องมือ | การทำงาน | ตัวอย่าง | Priority |
| --- | --- | --- | --- |
| แต้มสะสม (Points) | ได้แต้มตามยอดใช้จ่ายหลังหักส่วนลด, ตั้งอัตราต่างกันตามหมวด (บริการ vs สินค้า), แต้มพิเศษจากกิจกรรม (รีวิว, ชวนเพื่อน, อัปโหลดวัคซีน, วันเกิด), แต้มหมดอายุ (เช่น 12 เดือนแบบ rolling), แต้มรอยืนยัน (pending) จนกว่าบริการเสร็จ | 25 บาท = 1 แต้ม, 100 แต้ม = ส่วนลด 50 บาท | MVP |
| แลกแต้ม (Rewards catalog) | แลกส่วนลด, แลกบริการฟรี (ตัดเล็บ), แลกสินค้า, แลกคูปอง partner; แลกที่ POS หรือใน LINE | แลก 300 แต้ม = อาบน้ำฟรี 1 ครั้ง | MVP |
| Tier (Membership level) | เลื่อนระดับตามยอดใช้จ่าย 12 เดือนย้อนหลัง, สิทธิต่อ tier (ส่วนลด, ตัวคูณแต้ม, จองล่วงหน้าได้ก่อน, ฟรี late checkout), คำนวณปรับระดับรายเดือน + แจ้งล่วงหน้าก่อนตกระดับ | Silver 5,000 / Gold 15,000 / Platinum 40,000 บาทต่อปี | P2 |
| แพ็กเกจ (Prepaid package) | ซื้อล่วงหน้า N ครั้ง / N คืน ผูกกับบริการ + ขนาดสัตว์, วันหมดอายุ, ใช้ได้กับสัตว์ตัวไหน / สาขาไหน, ตัดอัตโนมัติตอน check-out, แจ้งเตือนคงเหลือและใกล้หมด — ใช้ได้ทุกช่องทาง (MoeGo ยังไม่รองรับบน mobile) | อาบน้ำ 10 ครั้ง จ่าย 8 ครั้ง, Daycare 20 วัน | MVP |
| Membership (Subscription) | จ่ายรายเดือนอัตโนมัติ (card on file), สิทธิต่อรอบ (อาบน้ำ 2 ครั้ง/เดือน + add-on ฟรี), สถานะ Active / Paused / Cancelled / Expired, พัก / upgrade / downgrade กลางรอบแบบ prorate, สิทธิที่ไม่ใช้ทบได้หรือไม่, สมัครเองใน LINE | Spa Club 990 บาท/เดือน, Daycare Unlimited | P2 |
| Wallet / Store credit | เติมเงินได้โบนัส (เติม 5,000 ได้ 5,500), รับเงินคืนจากการยกเลิก, แยกยอดเงินจริง vs โบนัสในบัญชี | เติมเงินก่อนหยุดสงกรานต์ | MVP |
| Gift card | ซื้อให้เพื่อนทาง LINE, มูลค่าคงที่หรือเป็นบริการ | บัตรของขวัญสปา 1,500 บาท | P3 |
| Referral | ชวนเพื่อนได้แต้ม/คูปองทั้งคู่เมื่อเพื่อนจ่ายครั้งแรก, กันโกง (เบอร์/อุปกรณ์ซ้ำ) | ชวนเพื่อน ได้ 200 แต้มทั้งคู่ | P2 |
| Stamp card (ดิจิทัล) | มาครบ N ครั้งได้ฟรี 1 — ทางเลือกง่ายสำหรับร้านเล็กที่ไม่อยากทำแต้ม | อาบน้ำครบ 9 ครั้ง ครั้งที่ 10 ฟรี | MVP |

**กฎที่ต้องกำหนดใน design**

- ยกเลิก / คืนเงินบิล → ดึงแต้มที่ได้คืน และคืนแต้ม/สิทธิแพ็กเกจที่ใช้ไป (reverse entry ใน ledger ไม่ลบแถว)
- แต้มและแพ็กเกจใช้ได้ทุกสาขาใน tenant เดียวกัน (ตั้งจำกัดสาขาได้) และรายงานหนี้ค้างระหว่างสาขา (ขายที่ A ใช้ที่ B)
- รายงานมูลค่าแต้มคงค้าง (liability) และอัตราการแลก, รายงาน member vs non-member (ความถี่, ยอดต่อบิล, retention)
- การปรับแต้มด้วยมือต้องมีเหตุผล สิทธิ์ผู้จัดการขึ้นไป และอยู่ใน audit log

## System Design

แนะนำเริ่มเป็น **Modular Monolith** (โค้ดเดียว แบ่ง module ตาม bounded context ชัดเจน สื่อสารผ่าน interface + domain event) บน PostgreSQL ตัวเดียวแบบ multi-tenant — ทีมเล็กส่ง MVP ได้เร็ว และแยกเป็น service ได้ทีหลังเฉพาะส่วนที่โหลดสูง (Messaging, Media, Partner API)

(แผนภาพ Architecture ในต้นฉบับ: 5 ช่องทางเข้า, 11 module, 4 ส่วน data/async)

Scheduling & Booking คือแกนที่ทุก module พึ่ง จึงควรออกแบบและทดสอบ concurrency ก่อนส่วนอื่น ส่วนการส่งข้อความ, webhook และการย่อรูปทำผ่าน queue ทั้งหมดเพื่อไม่ให้หน้าเคาน์เตอร์ค้าง

**Bounded context / Module**

| Module | ความรับผิดชอบ | Entity หลัก | Event ที่ปล่อย |
| --- | --- | --- | --- |
| Identity & Tenant | tenant, สาขา, user, role, permission, subscription | Tenant, Branch, User, Role, Permission, Plan | `user.invited`, `branch.created` |
| Customer & Pet | ลูกค้า, สัตว์, วัคซีน, waiver, consent | Customer, Household, Pet, PetWeightLog, Vaccination, VaccineType, Waiver, Consent, PetFlag, TemperamentEvaluation | `customer.created`, `vaccine.expiring`, `consent.withdrawn` |
| Catalog & Pricing | บริการ, add-on, rate plan, กฎราคา | Service, AddOn, PriceRule, RatePlan, RoomType, Season | `price.changed` |
| Scheduling & Booking | คิวช่าง, ห้องพัก, daycare capacity, hold, waitlist | Booking, BookingItem (pet × service), Resource (groomer / table / room / zone), Slot, Hold, Waitlist, Shift | `booking.created/confirmed/cancelled`, `slot.released` |
| Operations | check-in/out, task, care log, incident, report card | CheckIn, Task, CareLog, MedicationLog, Incident, ReportCard, Media | `pet.checked_in`, `incident.reported`, `report_card.published` |
| Commerce | POS, invoice, payment, refund, wallet, inventory | Order, OrderLine, Invoice, Payment, Refund, WalletLedger, Product, StockLedger, CashShift | `payment.succeeded`, `invoice.issued`, `stock.low` |
| Loyalty | แต้ม, tier, package, membership, referral | PointLedger, Tier, Package, PackageBalance, Membership, Referral | `points.earned`, `tier.changed`, `membership.renewed` |
| CRM & Marketing | segment, journey, campaign, promotion, coupon, inbox | Segment, Journey, Campaign, Message, Promotion, Coupon, Conversation, Lead | `campaign.sent`, `lead.converted` |
| Channel & Integration | channel manager, partner API, webhook, voucher | Channel, ChannelBooking, Partner, ApiClient, WebhookSubscription, WebhookDelivery, Voucher | `channel.booking_received` |
| Notification | ส่ง LINE / SMS / email / push ตาม template และ consent | Template, Notification, DeliveryLog | `notification.failed` |
| Reporting | read model / data mart สำหรับ dashboard | fact tables (sales, occupancy, utilization) | — |

**การตัดสินใจทางเทคนิคที่สำคัญ**

1. **กันจองซ้อน:** ห้องพักใช้ exclusion constraint บนช่วงวัน (`tstzrange`) ต่อ resource, คิวช่างใช้ constraint เดียวกันบนช่วงเวลา, การขายตาม room type ใช้ inventory counter ต่อวัน + row lock — ไม่พึ่ง check ในโค้ดอย่างเดียว
2. **Hold & expiry:** การจองออนไลน์สร้าง Hold 15 นาทีระหว่างรอมัดจำ หมดอายุแล้วคืน slot ให้ waitlist อัตโนมัติ
3. **Multi-tenant:** ทุกตารางมี `tenant_id` + PostgreSQL Row-Level Security, ข้อมูลระดับสาขามี `branch_id` เพิ่ม; tenant ใหญ่ย้ายไป schema/DB แยกได้ภายหลัง
4. **เงินและแต้มเป็น ledger:** Payment, WalletLedger, PointLedger, PackageBalance, StockLedger เป็น append-only; ยอดคงเหลือคำนวณจาก ledger, แก้ไขด้วย reverse entry, เก็บเงินเป็นสตางค์ (integer)
5. **Pricing service ตัวเดียว:** หน้าจอง, POS, Partner API เรียก quote จากที่เดียว และบิลเก็บ snapshot ของกฎที่ใช้
6. **Event-driven ด้วย Outbox pattern:** ทุก domain event เขียนลง outbox table ใน transaction เดียวกัน แล้ว worker ส่งต่อไป Notification, Loyalty, CRM, Webhook — ข้อความไม่หายแม้ระบบภายนอกล่ม
7. **Payment adapter + webhook-confirmed + idempotency:** สถานะจ่ายแล้วมาจาก webhook ที่ตรวจ signature และ retrieve ยืนยันซ้ำเท่านั้น
8. **Media pipeline:** รูป/วิดีโออัปตรงเข้า object storage ด้วย pre-signed URL, ย่อขนาด + ทำ thumbnail แบบ async, ส่งผ่าน CDN ด้วย signed URL อายุสั้น
9. **LINE หลาย OA:** เก็บ channel secret / token ต่อ OA ใน secret manager, webhook endpoint เดียวแยก OA จาก destination, LINE userId ต่างกันต่อ provider จึง map ผ่านเบอร์โทรศัพท์ด้วย
10. **Timezone & calendar:** เก็บ UTC, แสดง Asia/Bangkok, รองรับปฏิทินวันหยุดไทยและพ.ศ. บนเอกสาร
